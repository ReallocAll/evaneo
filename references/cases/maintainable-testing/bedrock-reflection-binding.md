# Bedrock Python binding: reuse generated reflection instead of a second schema compiler {#case}

## Reversed implementation {#change}

[EndstoneMC/bedrock-protocol PR #2](https://github.com/EndstoneMC/bedrock-protocol/pull/2) initially added a nanobind generator that traversed the schema and emitted C++ binding code per field/type/version, as well as Python modules and stubs for each version. In [3737018ed434](https://github.com/EndstoneMC/bedrock-protocol/commit/3737018ed4349e9e1116c7dfa6cce725dcc93cc0), the author reported approximately **6 MB of generated binding C++ per build**. This is a source-reported magnitude, not an independently measured benchmark. Each new schema DSL feature would otherwise need implementation in both the existing C++ generator and the new binding generator; the binding also could not build from release-generated headers alone.

The enabling [9853b97c448c](https://github.com/EndstoneMC/bedrock-protocol/commit/9853b97c448cd80f7b663b7402ba22a1d2dadc41) emitted generic C++ reflection capabilities: per-module versioned type lists, schema-preserved enum names, primitive alias information, equality and a shared packet-header serializer. Then [3737018ed434](https://github.com/EndstoneMC/bedrock-protocol/commit/3737018ed4349e9e1116c7dfa6cce725dcc93cc0) replaced per-field generation with one generic nanobind binder that traverses those emitted descriptions. It binds unchanged types once across versions, and handles leaf types not covered by reflection with dedicated casters. The resulting interface has explicit `v<N>` version modules and version-level encode/decode calls.

## Packaging as an architecture check {#package}

[82b8baadd098](https://github.com/EndstoneMC/bedrock-protocol/commit/82b8baadd098aa75093e7716f00b580efc7decf9) separates the end-user `bedrock-protocol` runtime from `bedrock-protocol-compiler`; the runtime wheel does not install the schema compiler. [7b9dbb8614de](https://github.com/EndstoneMC/bedrock-protocol/commit/7b9dbb8614dec6956c52d52bcb6e974bec1e0250) adds a consumer check that installs wheels outside the checkout and builds from a source package containing pregenerated C++ while the compiler, schema and uv are unavailable. The wheel contract uses `cp312-abi3` for CPython 3.12+. These checks exercise the *distribution boundary*, rather than only the checkout's build graph.

## Transferable decision {#judgment}

When one schema already produces enough C++ types, **extend its small reflective contract before introducing a second field-by-field generator**. Test this choice by building from the artifact a real consumer receives, with authoring tools absent. A generic binder is worthwhile here because multiple versions and schemas share a stable description; it is not automatically preferable for a handful of unrelated types or when reflection would obscure ownership, ABI or runtime contracts.

## Limits {#limits}

Source: [9853b97c448c](https://github.com/EndstoneMC/bedrock-protocol/commit/9853b97c448cd80f7b663b7402ba22a1d2dadc41), [3737018ed434](https://github.com/EndstoneMC/bedrock-protocol/commit/3737018ed4349e9e1116c7dfa6cce725dcc93cc0), [82b8baadd098](https://github.com/EndstoneMC/bedrock-protocol/commit/82b8baadd098aa75093e7716f00b580efc7decf9) and [7b9dbb8614de](https://github.com/EndstoneMC/bedrock-protocol/commit/7b9dbb8614dec6956c52d52bcb6e974bec1e0250). The source CI associated with PR head completed successfully, but the checks were not rerun for this record and do not establish live transport interoperability. The reflection approach also has compiler constraints: [6819e60f7508](https://github.com/EndstoneMC/bedrock-protocol/commit/6819e60f7508cc72f1f69c1042749a2efbf3b30c) reports a Clang-cl expression nesting limit and uses MSVC for the Windows wheel. Thus “less generated code” does not mean “zero compilation complexity.” The merged runtime uses mutable values and defaults to protocol version 2193 unless further versions are selected in CMake; do not treat the stale PR description's immutable/all-version wording as the final contract.
