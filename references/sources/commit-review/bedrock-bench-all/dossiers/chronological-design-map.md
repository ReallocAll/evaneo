# Chronological design map {#chronological-design-map}

Use the [public commit history](commit-by-commit.md) for source links, dates, and changes. This map groups related implementation evolution without collapsing later fixes into the initial design.

1. **Archive before generalization (000–007).** Historical Linux/Windows and cross-server scripts, mixed-provenance binaries/configuration, selected result records, and a long explanatory series are imported. Original experiments contain both useful measurements and failed intermediate verification, host contamination, incomplete source provenance and inconsistent workloads. Early documentation explicitly acknowledges lost raw directories and unknown binary/source correspondence. The new Python package/schema foundation is a separate implementation rather than a claim that the archive was reproducible as-is.
2. **Explicit workload and test interfaces (008–014).** Loadbot control/telemetry, metric fixtures, machine claims and server adapter contracts make assumptions concrete. Synthetic server/bot processes provide deterministic death, readiness, join and malformed-output cases. They are valuable interface fixtures, but shared fake generators/parsers and missing/xfail runner paths mean the suite is initially an intended contract. Fake movement, reconnect and jitter controls do not fully implement the real loadbot semantics.
3. **Isolation and lifecycle become first-class (015–019).** Process identity, CPU-set placement, telemetry, staged artifacts and finalization support a fresh process per run, bounded stages and retained invalid attempts. The full runner establishes idle/join/settle/spread/steady/teardown and rotation across repeats. Settlement depends on configured-denominator view growth and relative coverage, and interventions can happen during load. Zero growth, missing rows, weak acknowledgements and stale final data are important boundaries. Initial tests reject any bad shutdown as server failure; later history deliberately changes that policy.
4. **Broader implementations with explicit fidelity gaps (020–025).** Native LeviLamina and Dragonfly, followed by additional adapters/helpers and pregen, seek comparable inputs across incompatible runtimes. Helper/API behavior, command acknowledgements, terrain/AI work, native versus VM memory and build/version facts cannot be assumed equivalent. The Docker library branch introduces container process/network machinery and clock remapping, but the ordinary runner never becomes wired to execute that mode before its removal. This historical distinction prevents attributing container-run results to a library-only path.
5. **Consolidation without erasing provenance (026 onward).** Legacy and blogs are removed, the exact blogs restored, then configuration/schema/documentation are consolidated. Exact blobs establish what was copied or deleted. Later defaults and schema revisions should be read as versioned decisions; prose and implementation can briefly disagree. A selected published result subset is not the full original archive.
6. **Measured-data feedback revises the methodology.** Remaining history develops chaos controls, fixes bot telemetry/time alignment and chunk view interpretation, revises metric/fixture behavior, expands reports, reruns exported analyses and adjusts validity rules. Result exports are evidence of reported runs, not newly executed validation. Complete dataset/schema audits retain invalid attempts, missingness and comparability groups rather than treating a headline table as the entire experiment.
7. **Final policy and documentation boundaries.** Probe tolerance evolves from shorter 15-second/1-second thresholds to 60-second/30-second thresholds. Analysis version 2→3 separates postmeasurement bad stop into unclean_stop rather than poisoning an otherwise measured window. Final prose versus configuration includes a 180-second/10-second discrepancy that must be resolved by version-specific source rather than silently normalized. TPS sampling, CPU-per-tick, wall-time view latency, successful spawn, online population and applied stress work remain distinct quantities. Final methodology discloses synthetic workload limits and maintainer conflict; it does not establish general human-gameplay rankings.

## Safe synthesis constraints {#safe-synthesis-constraints}

Across this history the project makes fixtures, provenance, validity and phase boundaries more explicit, including corrections when measurements reveal mismatches. Counterexamples include permissive checks, synthetic fidelity gaps, unfinished Docker integration, policy reversals and failed runs. These observations describe code and published explanations; older Nukkit implementation history is outside scope.
