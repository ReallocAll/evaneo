# Benchmark methodology: what the measurements do and do not establish {#benchmark-methodology-what-the-measurements-do-and-do-not-establish}

Source: EndstoneMC/bedrock-bench at [commit 64a45c4ffbb2b9e29da6fd4676711eeaf5df450d](https://github.com/EndstoneMC/bedrock-bench/commit/64a45c4ffbb2b9e29da6fd4676711eeaf5df450d), including `docs/methodology.md`, `configs/spread.toml`, and the TPS/load metric implementations. This is static analysis, not a benchmark run or confirmation of reported measurements. The maintainers disclose their conflict as operators of a competing measured server.

## Controlled inputs are necessary but not sufficient fairness {#controlled-inputs-are-necessary-but-not-sufficient-fairness}

The final method drives one resolved workload configuration across servers. Reference: 100 bots, 300 ms join stagger, fresh world seed 20261010, view distance 10, simulation distance 4, survival/easy, max players 200, client-side terrain generation disabled, offline loopback login. Bots are placed on a grid whose origin is 1280, spacing 640 and column count 11 at y=300. Their circles, lack of real vertical physics, all-cache-miss behavior, and synthetic offline identities are a reproducible stress recipe, not a representative distribution of human survival play.

CSG off removes a large source of unequal network/terrain work among BDS-hosted and custom servers. It does not equalize work. Flat generators, absent mob AI, different terrain, physics and movement-validation implementations remain real confounders. Corrections triggered by an unrealistic flat walking client remain charged to the servers that implement validation. Memory comparisons across Go/native/PHP and fixed-heap JVM runtimes also differ in meaning.

Separate CPU sets avoid direct scheduling competition, but bots and servers still share last-level cache, memory bandwidth and power. Physical pinning is not equivalent to vCPU placement on WSL/VMs. The documented publisher uses Windows; Linux ordering need not match because scheduler, allocator and binary implementations vary. A 25-bot result cannot substitute for 100 bots, nor can a terrain-heavy result establish mob/redstone/building/combat capacity.

## Timing and phase boundaries {#timing-and-phase-boundaries}

The phase sequence is boot→idle→join→settle→spread→steady→teardown. Fresh process isolation per run prevents failed-run in-memory state from contaminating the next. Partial records survive interruption. Measured load spans first dial to settled; steady starts 15 s later and lasts 90 s. Settle runs at least 300 s after alljoined and at most 900 s, with a 60 s view-growth criterion checked every 5 s. Therefore settle duration is not a loading speed score: a fast server waits for the floor, while a stalled server can appear to have low growth. Incomplete views and capped settling must accompany measurements.

The prose permits bounded re-teleports/nudges during settle and prohibits interventions after settled, while rule R7 says none inside measured windows and the load window includes settle. This apparent documentation tension deserves implementation-level intervention-accounting review before treating R7 as proof that load samples are intervention-free. Do not silently reconcile incompatible prose.

`fc44a38` switches the harness clock helper to perf_counter_ns and routes stamp/test callers through it. Final bot timing uses a fitted offset: each hello separates a bot process, the smallest receive-minus-monotonic timestamp estimates its offset, and epoch timestamps are fallback. This avoids wall-clock midnight artifacts, but it does not remove communication/queue latency; offset fitting is an inference bound, not synchronized hardware clocks.

`5538725` relaxes probe gates from gap 15→60 s and steady p99 lag 1→30 s. Its explicit reason is that console commands wait on an overloaded tick thread; a busy server must not be rejected simply for being slow. This changes admissible runs and configuration identity, so historical classifications cannot be treated as timeless.

## TPS is an observed counter slope {#tps-is-an-observed-counter-slope}

`tps.replies` sorts receive-time samples. Window TPS takes the first/last replies inside the requested interval, requires at least 90% coverage, and divides executed-counter delta by receive-time delta. Counter decreases and idle non-advancement are validity checks; time-of-day is not an acceptable counter. Short interval rates can exceed 20 because replies jitter; code deliberately does not clamp. `lowest` searches the first later sample at least 4.5 s away for each starting reply; “lowest 5 s” is thus a jitter-tolerant interval statistic, not an exact sliding five-second hardware timer.

Final exported TPS has 422 samples above 20 of 2,287, and no negative samples. This is consistent with unclamped receive-time interval rates; it is not evidence that a server executes sustainably above the nominal 20 TPS target. Whole steady-window TPS is the appropriate throughput comparison. Tick-thread CPU/tick is explicitly CPU consumption and excludes blocked wall time, so it is not cross-server MSPT. Go servers with no single stable tick thread must use process CPU or mark tick-thread CPU not applicable.

## View load, censoring, and denominators {#view-load-censoring-and-denominators}

`metrics/load.py` uses in-view unique chunks, not lifetime chunks streamed before a teleport. At settled, each bot has final U_b. Own-view t90 is time from first teleport to ceil(0.9 U_b), using delta-encoded first-seen times where available; 5 s progress snapshots are fallback. A server delivering fewer chunks can win this metric while doing less work. Always retain final chunks per player alongside t90.

The implementation also contains an equal-count target (80 chunks), with incomplete observations censored at the bot's last observation. This is conceptually different from replacing missing players with zero latency. The report's headline uses own-view t90. Chunk throughput divides the aggregate settled view by the entire load duration; the 300 s settle floor compresses differences among fast-loading servers. These denominators must travel with any quoted values.

## Outcomes, gating, and recomputation {#outcomes-gating-and-recomputation}

The method distinguishes invalid harness/environment measurements from server failures. Invalid dominates server_failed when both occur; gates for unreached windows are skipped. Invalid runs may be retried once, server_failed is retained without automatic rerun. Hence multiple rows for the same repeat can be invalid/retry history, not independent clean repetitions.

`b25964a` raises analysis version 2→3: nonzero exit or forced kill after the measured windows becomes `unclean_stop`, while death before teardown remains server_failed. `5695726` fixes legacy recorded exit-code reasons that otherwise continued to force the old failure on recompute. The recorded Nukkit-MOT ce235ee run moves from 0/1 to 1/1 without a new underlying run. That is an analysis-policy correction, not a server performance improvement.

Final config gives servers 10 s to stop. The final methodology phase table still says 180 s. The same document still describes Chorus as excluded for decode errors and older-protocol servers as waiting for a build; later pins re-enable Chorus and exclude Allay/PocketMine for protocol support. Prefer the specific code/config and commit evidence over stale narrative snapshots.

## Reproducibility boundaries {#reproducibility-boundaries}

Per-version artifact hashes, runtime pins, recorded launch argv/environment modifications, per-key before/after configuration, fresh install copies, and result hashes are strong audit affordances. They do not themselves prove raw material is published or experiments reproducible. This review reads exported summaries/CSVs and source; it has not executed analyze or obtained every raw run directory.

The narrowed dirty check (`adb72b4`) only examines tracked changes under four folders. Untracked inputs and changes elsewhere may escape that flag; clean is not a cryptographic proof of the complete execution environment. Reports reject mixed config/machine/profile/analysis versions according to documentation, but exported environment tables show multiple harness commit IDs. That is disclosed provenance, not proof those commits were semantically equivalent.

A same-machine comparison is most defensible within matching versions, configuration/analysis definitions and complete repetition sets. ## Initial host control and measurement substrate (ordinal 15, 6d8cb52e) {#initial-host-control-and-measurement-substrate-ordinal-15-6d8cb52e}

### Placement and exclusivity {#placement-and-exclusivity}

Automatic placement prefers the fastest core class for the server and slower cores for bots when at least four logical bot CPUs exist. Homogeneous machines reserve roughly a quarter of physical cores, with minimum four logical bot CPUs and a half-machine ceiling. Whole SMT sibling sets are normally kept together. Explicit harness reservation can split a physical core; explicit server/bot sets need only be logically disjoint, and shared SMT receives a warning. Four logical bot CPUs is a planning heuristic, not demonstrated spare load-generator capacity. Verification requires exact process affinity and permits thread-affinity subsets, skips unreadable thread affinity, and checks process priority rather than every thread's nice value. Windows processor groups above 64 CPUs are refused; a topology API fallback treats each logical processor as its own core and can lose SMT information.

Unknown virtualization is treated as physical. Windows VBS/Hyper-V host use and Linux containers can consequently appear bare-metal; detected VMs receive warnings. The port bind check has the usual check-to-launch race. Go minimum version and power-state diagnostics are advisory. On Linux, selecting normal priority does not reset a nonzero inherited nice value because the pre-exec hook only sets nonzero requested nice. This is a static boundary of the initial implementation, not a reproduced failure.

The lock is an OS advisory lock at a selected cache path, with metadata and an inherited token. It coordinates processes using that same path, not all possible cache roots. A token-bearing child checks the parent's lock instead of owning it; parent death can release exclusivity while the child continues. Multiple authorized children may share the token. A metadata-write error after acquisition is another cleanup-sensitive path. Tests cover ordinary holder contention, inheritance and release, but do not establish whole-tree exclusivity after parent death.

### Process and platform contracts {#process-and-platform-contracts}

Windows starts suspended, attaches a kill-on-close job, sets affinity/priority, then resumes. Job attachment failure warns and proceeds, so the strong cleanup promise is conditional. Linux starts a new session/process group without a parent-death signal. A server spawned by a launcher can require post-launch placement, especially Windows priority, so first-instruction placement of the launch root is not necessarily first-instruction placement of every descendant. DeathWatch polls, and marking expected exit can race an already-occurring death. The kill-tree return value lists initially alive PIDs rather than verified remaining survivors despite its wording.

Linux favors schedstat nanosecond thread CPU when the file exists, without separately establishing that accounting is enabled and advancing; fallback uses CLK_TCK. Parsing handles parentheses in comm and uses process start identity. Unreadable/vanished thread rows are skipped, and no remaining rows becomes ProcessGone. Tick readers keep an open file descriptor. Linux private memory is anonymous RSS plus swap, whereas Windows private bytes are commit-oriented: these columns cannot be casually compared as the same quantity.

Windows uses fixed x64 native system-information layouts and a bulk query, with comments explaining avoidance of per-thread GIL overhead. Acquired handles protect against TID reuse; unavailable handles weaken that identity protection. An unavailable final CPU read can emit zero. Names refresh periodically and cached modules can become stale after unload/reuse. Creation times map wall time to monotonic time using a sampled offset. Cycle calibration uses short busy-loop rounds and takes the maximum observed rate; it is not an independent proof of invariant TSC frequency. Platform-specific tests exercise thread descriptions, final rows and plausible calibration only on eligible hosts.

### Accounting, time and missing work {#accounting-time-and-missing-work}

Periodic samplers use absolute deadlines, skip overruns, preserve unexpected errors and attempt a final sample. Stop joins for a bounded period without necessarily marking a still-running sampler failed. The sidecar's done summary omits overruns; a broken heartbeat pipe or a valid non-object JSON command has separate failure paths. Selecting a target by first matching executable assumes the namespace is controlled.

Process groups subtract CPU already present at discovery, retain the last observed counters after exit, and refresh membership on slower schedules. Consequently pre-discovery child work, short-lived descendants and CPU between the last read and death can be omitted. Retained orphan membership and later root reassignment need care to avoid double accounting. Whole-machine foreign CPU subtracts asynchronously observed owned-process CPU from machine busy time and may be negative; Linux steal is included in busy while iowait is idle. Server-set foreign CPU assumes the entire server tree remains pinned. Newly discovered owned children can initially be charged as foreign. A newly readable foreign process is treated like a newly started process and its whole prior CPU history can enter a diagnostic top list. Idle measurement does not continually refresh new descendants. CPU hotplug and noncontiguous CPU-column reconstruction are further fixed-topology assumptions. Process sample fields are collected sequentially, not at one atomic instant.

The tick probe pairs replies FIFO without correlation IDs. Expiring old requests limits some drift but cannot prevent a lost reply from pairing the next reply with the wrong send before timeout; a late expired reply can also consume a newer request. Expiration does not cancel queued console commands. An unstamped reply falls back to queue time and is counted; unsolicited matching lines can be consumed. Tick-rate differences may remain usable while request latency is wrong. Tests explicitly cover ordered replies, timeout, unmatched and unstamped replies, rate calculation and broken-pipe shutdown. They do not prove arbitrary loss/reordering correctness.

Series writers zero gzip timestamps and tests compare identical simple writes, but different flush schedules can still produce different compressed bytes. Recovery readers keep complete rows before truncation; they read the first gzip member, discard a plain-text unfinished line, and skip ragged rows. Thread CSV omits alive state, creation time and start module even though the live reader knows them, limiting retrospective identity reconstruction. The JSONL writer opens in write mode despite append-only wording. Tests cover format round trips, quoted thread names, ragged rejection, cut gzip recovery and flush visibility. A submitted live CPU-burner test checks positive CPU deltas, sampler rows, pinned busy cores and exclusion from foreign-top lists. These are sensible integration assertions, not evidence that every supported OS/version or actual Bedrock workload passed them.

### Phase boundaries and interventions {#phase-boundaries-and-interventions}

Placement waits for both a bot spawned event and a server entered-world line, in either order, resetting on dial/rejoin. It queues effects and teleport and records the placement time immediately after enqueue. Therefore that time is not an acknowledged server-side teleport time. Boot requires readiness and rejects an observed mismatching banner, but a missing banner is allowed at this stage. Tick-thread discovery tries at ready and again before join. Alljoined is recorded at harness receive time and only zero successful joins immediately aborts; partial failure is evaluated later by health gates.

Settle is a pure state machine fed receive-time progress, teleport events, departures and queued placements. Growth is the change in summed unique chunks divided by elapsed snapshot time and configured bot count. It uses the newest base at least a window back, or oldest available data when history is short. Falling totals, missing rows or reconnections can produce a low or negative growth rate; quiet does not mean a complete view. View completeness is relative to half the median among rows present, not an absolute expected disc and not divided by configured bot count. All-zero views can have 100% relative completeness. Minimum-view-share enforcement defaults off; the cap can finish with stale data. These limitations are especially important when servers do different chunk-generation work.

A missing teleport acknowledgment triggers up to three reteleports, separated by 20 s. Hovering bots above y=290 with fewer than 30 unique chunks can receive two nudges after 60 s, alternating one chunk away and back; the holdoff follows their last placement/nudge. Once done, automatic placement is disabled until an optional chaos phase. The persisted in_measured intervention count is hardcoded zero in the state machine, rather than derived from actual journal send times. The drain waits up to 30 s but does not fail if backlog remains, and queue completion does not prove command execution/acknowledgment. Thus the stated intervention-free steady interval is an intended invariant with bounded-drain assumptions, not an unconditional guarantee.

Spread maps x/z positions to nearest cells and checks unique occupancy; it ignores dimension, y, player identity-to-intended-cell assignment and exact distance except for a warning. A bot can be far from its center yet pass occupancy. Position acquisition prefers adapter queries, falling back to bot reports. This verifies a useful distribution property, not terrain equivalence, movement validation or complete loading. During the steady sleep only server death is checked; bot exit is not actively polled there, leaving final bot metrics/health to diagnose it.

### Failure, persistence and evidence {#failure-persistence-and-evidence}

Session catches ordinary phase/harness exceptions, then attempts teardown and collection separately. Bots stop before the server is marked expected-to-exit; shutdown escalates from console stop to interruption/tree kill. Early server death, nonzero exit and never-ready handling retain crash artifacts and tail. In this initial era a bad stop contributes server_failed; later analysis-version changes distinguish post-measurement unclean_stop. Do not apply those later classifications retrospectively without version-aware reanalysis. Teardown or collection exceptions are recorded, but one failure within the sequential collector can prevent later collection steps. The stronger prose that every outcome after directory creation is recorded also has a boundary: provenance/record creation and finalization can themselves fail outside the main measurement exception handling.

Run directories are uniquely created and raw files retained; partial JSON is replaced atomically, then a provisional run record allows the same raw loader/metric engine to derive final status. Formula failures produce invalid records. Atomic rename prevents torn JSON, but there is no fsync durability guarantee. The raw-file manifest hashes bytes and sizes, excluding record files and temporary files. Validation checks declared hashes and stray files; ordinary load_run does not first verify hashes and accepts missing series as empty. It uses the currently installed adapter dialect, so identical raw data with a changed dialect or analysis version need not produce identical interpretation. Schema compatibility is checked by top-level schema identifier, not complete validation on load. Partial records are written before final scrubbing; raw logs/configs/crash artifacts are not scrubbed by the final run.json scrubber. Moreover live reasons are assigned after the initial record scrub, so success-path reason privacy should not be inferred from the blanket prose promise.

Unit tests exercise grid ties/occupancy, ordered placement signals and rejoin clearing, deterministic order/subsets, destination mismatches, bot override flags, synthetic snapshot settle limits/interventions, schema examples, hash tampering, concurrent event writing and recomputation against generated goldens. One test deliberately strips machine.gates because the then-current schema did not yet list it. Smoke checks movement corrections against declarations and associates error/fatal lines within two seconds with commands; absence of such errors is not positive acknowledgment, and unrelated nearby errors may be attributed. Smoke failure returns invalid after normal run finalization without rewriting that run's otherwise-ok status. These tests specify bounded wiring expectations; synthetic fixture recomputation is consistency evidence, not independently measured server performance.
