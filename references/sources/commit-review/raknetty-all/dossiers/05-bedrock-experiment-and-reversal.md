# Bedrock extension, incomplete refactors and scope reversal {#bedrock-extension-incomplete-refactors-and-scope-reversal}

## What was actually added {#what-was-actually-added}

The original implementation targeted RakNet. [C17](../commits/017-97a60d613446.md) introduces a Minecraft-oriented offline MOTD provider; [C33](../commits/033-7d52b850ceb9.md) renames that module to Bedrock and expands into channels, packet IDs, login decoding, compression/encryption placeholders and variable-length integers. A list of known packet identifiers is not an implemented feature matrix. At that stage important encoders and encryption are TODOs, and the batch parser reads a length without using a bounded slice.

[C35](../commits/035-398af46ee855.md) supplies a much larger protocol experiment: separate RakNet connect and Bedrock login futures, EC key setup and shared-key derivation, AES-CTR encryption, counter-based truncated digest checks, handshake messages, offline self-signed client login, JWT chain utilities, disconnect reasons and packet framing. The server handshake is sent before enabling encryption, while the client sends its response after enabling it. That ordering is an explicit source reason: encrypting the initial key-establishment handshake would prevent the peer from reading it. Online/console client login is explicitly unsupported. Three credential-guarded lines are opaque, so the cryptographic source is not wholly inspectable and no security audit or secret exposure claim is made.

Batching runs on a 20Hz queue and uses length-framed packet slices with compression transforms. [C36](../commits/036-490abddec457.md) separates batching from login/packet dispatch and retains a slice before forwarding it beyond the parent buffer's lifetime. [C37](../commits/037-d49e13f37326.md) centralizes identifier ownership and splits RakNet/Bedrock contracts. [C38](../commits/038-8e4215e4234d.md) adds resource-pack, inventory, player-list, skin, cache and time packets. Resource-pack responses say download finished/ready while the actual download work is not implemented. [C39](../commits/039-ce529bc7d4f8.md) adds supplier factories, a ByteBuf wrapper and serialized model classes, yet StartGame contains empty encode and comments rather than a functioning implementation. A successful-looking class or status enum therefore does not establish a full client session.

## Refactoring did not uniformly preserve behavior {#refactoring-did-not-uniformly-preserve-behavior}

[C36](../commits/036-490abddec457.md) initially leaves a prelogin handling TODO where prior gating existed. [C39](../commits/039-ce529bc7d4f8.md)'s dispatcher reports unexpected login state but continues dispatch; the status comparison itself requires checking. The server adapter's new `registerPackets` override is empty. Authentication exceptions are caught/logged, with no universally completed failure future. Unknown-ID/error early returns are not all protected by release. These observations limit any claim of a finished secure session pipeline.

Codec migrations also introduce or retain test candidates: [C37](../commits/037-d49e13f37326.md) duplicates UTF8 output, fixed by [C38](../commits/038-8e4215e4234d.md); [C38](../commits/038-8e4215e4234d.md) experiment count uses intLE on encode and VarInt on decode, fixed by [C39](../commits/039-ce529bc7d4f8.md); [C39](../commits/039-ce529bc7d4f8.md) player UUID endian changes, nonadvancing login-string reads and raw-versus-length-prefixed image/checksum output are not accompanied by regression tests. See [wire contract case](03-buffer-and-wire-contracts.md). They are static concerns attached to historical revisions, not claims about a deployed server, exploitability or present-day behavior.

The wrapper import is explicitly Netty-attributed, and the shared value types depend on contemporary `nukkit-api`. No inference about old excluded Nukkit implementation is needed. Nor should the wrapper's hundreds of delegating methods count as hundreds of target design decisions. The complete import was inspected proportionately and retains its attribution.

## The reversal is central evidence {#the-reversal-is-central-evidence}

[C40](../commits/040-b1629bfe80ba.md)'s message says to move raknetty-bedrock to nukkit-core. In this repository it deletes 55 files / 5,265 lines, retargets example imports/dependencies and exposes protected RakChannel construction hooks. Blob identity ties the deletions to versions already read. The destination repository's contents were not inspected, so this establishes removal and a stated destination, not a verified behavior-preserving migration.

[C41](../commits/041-4b7d7cc0176b.md) disables example building temporarily. [C42](../commits/042-e0ef690d3167.md) removes the aggregate all-in-one module. [C43](../commits/043-24a3e0a1e1fe.md) flattens the remaining transport into one root artifact and removes Bedrock client/server examples. Final core retains a small example MOTD payload and a forwarding demo, but not the removed application protocol implementation. Consequently, neither the large transient Bedrock diff nor its title can be used to describe final RakNetty feature parity.

## Usable lesson and limits {#usable-lesson-and-limits}

When a transport library begins absorbing an application protocol, name the responsibilities and make scope changes explicit: shared transport state, application login state, model serialization, crypto sequencing and application handlers have different contracts. An extension may be justified; later extraction may also be justified. The source does not explain every motivation for the move, so do not invent a general preference for minimal libraries or a personal rejection of layering.

Before extracting such a module, verify source/destination equivalence, compatibility fixtures, promised public API, failure futures, buffer ownership and dependency boundaries. None of those checks was demonstrated by a test suite here. This historical case is most useful as a refactoring checklist with counterexamples and reversals. The only thread-level confirmation is Issue #1's self-report, not verified parity or performance. All crypto, network and performance conclusions remain static or reported; no upstream code was executed.
