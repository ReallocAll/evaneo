The public import commit above is the source for the paths discussed below; detailed blob-identity comparisons remain historical static inspection, not independently reproduced here.

## What belongs to whom {#what-belongs-to-whom}

The 372-file `legacy/bots/gophertunnel-fork/` subtree is compared against upstream [Sandertv/gophertunnel v1.62.0](https://github.com/Sandertv/gophertunnel/tree/7a556a07335b663744b50d38062636ad8283f314), commit `7a556a07335b663744b50d38062636ad8283f314`, obtained through a read-only public Git fetch. Git blob identities establish 362 unchanged files, eight modified files, and two added files. Upstream's proxy `config.toml` and illustration `gophertunnel_telescope_coloured.png` are absent from the vendor subtree. The imported MIT license credits Sandertv, copyright 2019. Protocol implementations, parsers, tests, authentication code, dependency pins and repository policy copied unchanged are upstream work, not evidence of Vincent's individual authorship or endorsement of every detail.

`legacy/bots/gtfork/go.mod` and `main.go` exactly equal v1.62.0's corresponding blobs. `legacy/bots/gt1001/go.mod` and `main.go` exactly equal v1.57.1, commit `85f39490288ab0b7cc9de4f447a9013dd0ec16e0`. Both `main.go` files are the same upstream proxy example blob `941dad0dd3528ec928b32f195524230de2aba345`: obtain an account token, listen locally, connect upstream, synchronize StartGame/DoSpawn, and forward packets both ways. They are not the missing protocol-specific loadbot implementations. The module files use the upstream module identity and lack the imported implementation tree in those directories. A directory named “gt1001” therefore does not establish the historical protocol-1001 bot's exact code.

The review does not assign all imported configuration comments to the target either. Those files preserve software defaults and experiment overrides; upstream-generated prose may survive unchanged without indicating an independent design choice.

## Eight local protocol deltas, all read with surrounding code {#eight-local-protocol-deltas-all-read-with-surrounding-code}

A prior independent diff used original Git bytes, not credential-sanitized strings, to avoid false differences from redaction. The eight observed deltas are described below; the original comparison has not been independently rerun here.

1. `minecraft/conn.go` adds a package-global `RequestRadius`, default 16, used when `handleItemRegistry` sends `RequestChunkRadius` during spawn. The bot sets it once before starting connections. This solves process-wide initial-radius configuration, but couples every connection and casts the max radius to an unsigned byte without local range validation. It is not a per-connection API. The later documented replacement is a normal radius request after spawn; that change moves request timing, which must remain visible when comparing experiments.
2. `minecraft/nethernet.go` removes authentication-environment discovery and hardcodes identity domain `self`, only when the caller did not supply an identity. It also eliminates that discovery failure path. The benchmark bots dial `raknet`, so this branch is not exercised by their selected transport. Carrying it does not demonstrate a benchmark need.
3. `minecraft/protocol/info.go` changes the advertised game-version string from 1.26.50 to 1.26.51 while keeping protocol 2193. This changes client login metadata, not the protocol numeric version.
4. `minecraft/protocol/item_stack.go` replaces optional filtered custom-name text with an unconditional string in `StackResponseSlotInfo`, changing the response wire layout. Container response context and durability checks were read. These bots do not issue item-stack requests; no reproducing packet or dedicated test is supplied with the legacy change.
5. `minecraft/protocol/reader.go` and `writer.go` both remove the `Hand` byte from use-item inventory transactions. The remaining action/trigger, block, item, position and prediction order is unchanged. Symmetric removal makes local encode/decode consistent but does not itself establish compatibility with a particular server wire format. This bot sends movement and command requests, not item interactions.
6. `minecraft/protocol/sub_chunk.go` replaces the typed 16×16 height-map reader with a fixed 272-byte `[]int8` block for both maps. Upstream v1.62.0 already consumes 16 rows, each containing a one-byte varuint length of 16 plus 16 heights: 16×17=272 bytes. The legacy code preserves consumption length for well-formed inputs while discarding row-length validation and semantic row interpretation. It is not evidence that upstream's valid layout consumed the wrong number of bytes. The later repository documentation drops this workaround and names a wire-layout test; that later test was reviewed separately, not executed here.
7. `minecraft/protocol/packet/clientbound_update_sound_data.go` makes all seven sound-update slots optional union values, replacing seven mandatory `SoundDataUpdate` marshaler calls. Each slot can represent any variant; the field name does not constrain the wire value. No benchmark sound-update reproduction appears in this legacy source.

Eight changed files are represented by seven bullets because reader/writer form one symmetric change. Exact delta attribution does not establish who first authored each local line: the root commit imported a preexisting harness. No standalone patch history or local test results accompany these edits.

## Full loadbot versus earlier loadbot4 {#full-loadbot-versus-earlier-loadbot4}

Both added programs were read in full: `cmd/loadbot/main.go` and `cmd/loadbot4/main.go`.

The full bot staggers offline joins (default 300 ms), gives each logical bot a UUID, and reuses that UUID across reconnects in the same run. It enables the client cache but reports every received blob as missing. It refuses resource-pack downloads. Each bot moves at 20 client updates/second using a small circular horizontal motion with no local gravity integration; authoritative correction and move packets reset position. This is synthetic protocol traffic, not a game client rendering, caching terrain, or reproducing all player simulation.

The newer implementation sends loading-screen start/end after spawn and dimension-change acknowledgements after a one-second timer. It handles teleports/reset flags, health/death notifications, respawn-ready packets with up to three delayed retries, explicit reconnect control, reconnect-on-drop, radius jitter, optional latency probes and optional player commands. The earlier `loadbot4` lacks loading-screen completion, controls, reconnect/respawn handling, per-bot terrain accounting, and CSG flags. It requests only subchunks -4..5 and begins the movement tick at server GameData.Time; the full bot starts its own tick at zero and derives the vertical subchunk request range from SubChunkLimit (falling back to -4..19). These are different workloads, not redundant file versions to collapse blindly.

The full bot advertises CSG capability with `CompatibleWithClientSideChunkGen`, MaxViewDistance 96, and memory tier 4 when requested; it does not itself generate the missing terrain. Therefore receiving fewer server chunks under CSG is not independently proof of a complete equivalent view.

## Accounting and lifecycle caveats supported by the implementation {#accounting-and-lifecycle-caveats-supported-by-the-implementation}

- `ALLJOINED` is printed after successes+failures reach the requested count, or after three minutes, or cancellation. The marker is not a promise that all requested bots are online. A harness that waits only for that string can proceed with failed joins.
- Initial login/spawn has a combined 60-second context deadline. Initial failures do not retry. Rejoin failures retry after three seconds up to five consecutive failures. A successful but immediately dropped session resets that failure streak, so repeated successful short sessions are not bounded by that limit.
- Per-bot unique chunks are counted only after a teleport, keyed by X/Z alone. Dimension is absent. Per-session state is replaced on reconnect; the fleet cumulative unique counter is not reset, so per-bot final counts and fleet totals answer different questions during churn.
- A `LevelChunk` envelope counts even when terrain is delivered via subchunk/cache paths. The code asks for subchunks and always declares blob misses but never validates terrain contents as a full client would.
- Per-bot BOT dumps occur every minute, with a final dump. “90% of view” derived from these dumps is quantized and relative to each bot's eventual observed count. An incomplete view can still reach 90% of its own small denominator.
- STAT online is joined+rejoins−dropped−left. `dumpPackets` uses joined−dropped only, omitting voluntary leaves and rejoins. After churn it can misstate per-bot rates or divide by zero/nonpositive counts. The first STAT rates also divide cumulative traffic since startup by ten seconds, even though join time preceded that sample.
- Radius probes associate a single outstanding request with any radius-updated reply. Radius jitter or unrelated updates can satisfy the probe; timestamped NetworkStackLatency probes tolerate three unit interpretations. These are application/protocol response measurements with interference risk, not transport ping.
- Many packet writes/flushes are intentionally ignored. Delayed respawn/dimension timers and command goroutines are not joined on session shutdown; timer callbacks may write to closed connections. This is a lifecycle limitation inferred from control flow, not an observed crash.
- Global jitter randomness is not the Python chaos scheduler's seeded RNG. Setting a chaos seed does not seed the whole distributed experiment.

## Applicability {#applicability}

Use this evidence when auditing a benchmark dependency fork, reconstructing a protocol workload, interpreting client “online” and chunk counters, or planning session-cancellation tests. Prefer small explicit protocol changes with a failing wire fixture and a removal condition. Preserve actual client flags, compiled binary hashes, upstream identity, and session accounting. Do not generalize these historical workarounds into production protocol advice or personal preferences.
