# Release provenance is a sequence of states, not a workflow label {#s3-release-provenance-is-a-sequence-of-states-not-a-workflow-label}

## Evolution visible in source {#evolution-visible-in-source}

The repository first adds metadata, entrypoint and template package-data (`7801acd059ac110bc588c945f9239c2fc86b599e`), then separate CI/publication workflows (`dfc246c8b8a58d5ca96851aa17c15d264ba1634d`). It quickly replaces release-event publication with manual dispatch (`3b7114dae4747887171446dc7c46ca72d0e60dae`). CI temporarily shrinks to Python 3.12 (`bb0e9385c946fd3c74f1662b4c065f2d676b7726`) and later restores 3.11–3.13 with fail-fast disabled.

The final major workflow redesign validates an X.Y.Z input, rejects an existing tag, requires nonempty Unreleased notes, prepares version/changelog edits and notes, then commits, tags, pushes and creates the GitHub release. The dependent publish job checks out the generated exact tag and builds/publishes from that ref. This makes the source revision intended for PyPI explicit and auditable.

## What it establishes and what it does not {#what-it-establishes-and-what-it-does-not}

The workflow files establish configured ordering and permissions. They do not prove a release ran, a tag was uploaded, PyPI accepted the wheel, or a user installed it. Trusted publishing replaces a long-lived PyPI credential with the configured OIDC flow, but this review neither creates nor validates that external trust configuration.

The release operation is not transactional:

1. Local files are updated and committed.
2. Main and tag are pushed separately.
3. GitHub release is created.
4. A later job builds and publishes.

A failed build/publish can leave a published tag/release without a PyPI distribution. A push or release error can leave a partial earlier state. Existing-tag rejection prevents accidental repetition but also means a recovery procedure must distinguish a legitimate partial release from an attempted duplicate. Dry-run skips those mutations and does not reach the separate publish build, so it is a preparation preview rather than full delivery validation.

## Dependency and testing distinctions {#dependency-and-testing-distinctions}

`7cfbdca8b3c5d2b6761150bc904eb9a822b0f840` declares Ruff as a development group; `a21d550b4d85fb8ab77f9b43985bf18a9984c87f` immediately changes to an optional dev extra and aligns `uv sync`. There is no explicit general packaging rationale. Preserve the reversal instead of inferring a permanent author preference.

The intervening `2f66fb0347a3c81e70e33af7c3627c6f0a0e4cdb` widens uv_build compatibility and is authored by Dependabot, despite a merge-style subject. Its exact message and diff are retained in context provenance. Do not assign that dependency decision wholly to the target because later commits inherit the file.

Adding pytest and regression tests in S2 does not add a pytest command to CI. Build checks packaging compilation/configuration, lint checks source style, and model tests check a different contract. None substitutes for a native binding fixture or installed-wheel template/entrypoint smoke test.

## Useful recovery questions {#useful-recovery-questions}

When diagnosing a failed release, identify the furthest observable state: source commit, remote main, tag, release object, artifacts, package index. Rebuild from the exact intended tag rather than the moving default branch. Before retrying a mutating step, check whether that step already succeeded. These are inferences from the visible ordering, not claims that this particular project experienced such a failure.

When changing this pipeline, test invalid versions, duplicate tags, empty changelog, dry-run, publish failure after tag creation and wheel template inclusion. Do not run the upstream release workflow merely to validate its shape. No workflow or package code was executed.
