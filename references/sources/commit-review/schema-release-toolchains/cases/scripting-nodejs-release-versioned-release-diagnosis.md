# Version a compatibility claim, and correct it when the evidence changes {#n1-version-a-compatibility-claim-and-correct-it-when-the-evidence-changes}

## Evidence class {#evidence-class}

This repository distributes documentation and sample packs for a closed-source scripting plugin. Its commits establish public claims, diagnostic contracts, examples and corrections. They do not reveal the native runtime implementation. No binary, Node runtime, Minecraft server or hidden parity harness was run. [All 40 source dispositions](../scripting-nodejs-release-review.md) preserve this distinction.

Existing issue reviews are reused with exact raw-source SHA256 equality in reuse proof:

- #1: AdemonG1tHub reports a Windows crash importing mongodb; the existing reviewer inspected the screenshot, but it is not an independent exception trace or proof all npm imports crash.
- #2: the same reporter shows missing `libc++.so.1` on fresh Ubuntu 24.04 with QuickJS fallback. This is a deployment dependency failure, not evidence Node activated and then executed incorrectly.
- #3: reload crashes through V8/native-runtime lifetime-related frames. The trace narrows investigation to reload/lifetime but does not prove the exact ownership defect.
- #4: warpanda1 requests new Bedrock support. The reply promises next-release support; no mechanism follows from the request alone.

The release notes connect these reports to claimed fixes. Closing an issue and saying “next release” is not independent proof of the eventual asset or behavior.

## Preserve the watchdog reversal {#preserve-the-watchdog-reversal}

1. Initial README and 0.1.0 changelog claim runaway and over-allocation protection. Those broad claims are not accepted as validated facts merely because a later changelog repeats them.
2. October administrator/troubleshooting rewrites state that runaway handlers freeze the server, contradicting the earlier promise. The memory claim initially survives.
3. `c3b1e8cd4f0e961e4a685e36a2c386b2f8807212` reports that finite 15-second loops at top-level and in a handler both completed without interruption on the tested Bedrock 1.26.51 setup. Docs extend the hang warning to top-level load. The revised explanation still speculates that an execution-terminated message could indicate memory enforcement.
4. `7a945d0409caf8bf3ab498d85352d3014550110f` reports a more discriminating control: with a 100 MB setting, the built-in engine stops while Node holds 600 MB. It withdraws the memory-enforcement claim and removes the speculative explanation of the generic termination message.
5. 0.2.0 docs (`7b1f4add...`, `cc882ccf...`, `9891065a...`) say hang, heap and uncaught-overflow protection now works. The described scope is per-pack JavaScript heap; large external buffers are not counted, worker threads are unwatched, and an overflow caught by user code is not reported. By default reported watchdog failure can shut down the server. These are qualified release assertions, not a runtime validation result from this review.

The learning is the correction process and test discrimination, not “the watchdog always works” or “the watchdog never works.” A generic log string is insufficient to choose between hang, memory and externally requested termination. Comparative experiments require version, settings, entry point, control engine and observed outcome.

## Other meaningful contract revisions {#other-meaningful-contract-revisions}

- `/reload` begins as a crash risk, is described as refused in an intermediate release draft, then 0.2.0 says it works. Do not keep the intermediate refusal as current policy.
- `process.exit()` initially abandons work with a poor error and can stop Node timers/network callbacks; later docs say it throws a catchable explicit error without those side effects. No native mechanism is visible.
- CPU profiling moves from unavailable to claimed working; debugger attachment remains unavailable. `36eba983...` removes a stale profiler troubleshooting entry. Profiling and interactive debugging are different capabilities.
- `/nodejs` is first described as showing per-pack heap/watchdog state, then `74cf41d3...` narrows it to plugin/Node versions and active/inactive. Diagnose from its final observable contract, not an earlier draft.
- Compatibility changes from strict listed-version refusal to best-effort attachment outside tested builds. The advertised family becomes 1.26.5x, but stated test points remain 1.26.51 and 1.26.52. A wildcard support label does not establish tests on every patch.
- Final diagnostic prefix is `[Scripting] [Node.js]`, after an intermediate `[scripting-nodejs]` prefix. Exact messages matter when searching logs.
- Linux distribution support is separate from Endstone support: docs specify glibc 2.35+, and 0.1.0 needs LLVM C++ runtime installed while later packaging carries its own. These are versioned packaging claims. ARM/macOS Docker emulation was explicitly untested in earlier docs; absence of that sentence from a later shortened README is not independent test evidence.

## Diagnosis designed around discriminating observations {#diagnosis-designed-around-discriminating-observations}

The revised bug form requires version fields, OS, with/without-plugin outcome, expected/actual behavior and startup log. “Not checked” is an accepted control answer; a required field does not imply a performed test. A minimal pack remains optional. Troubleshooting distinguishes missing plugin, missing runtime directory, mismatched runtime/plugin versions, loader dependency failure, failed hook attachment and failing pack import. All can make a feature look absent, but their next actions differ.

The cross-engine engine-check sample safely imports only Minecraft API and optionally reads `globalThis.process?.versions`. This can establish which engine the pack sees without making an unconditional Node import fail first. Active engine is narrower than API parity or correct watchdog enforcement.

## Applicability and limitations {#applicability-and-limitations}

Use the case when maintaining a binary plugin, native binding, loader or compatibility layer with sparse diagnostic reports. Ask for the full startup path and a minimal comparison, publish precise version-qualified limitations, and preserve historical corrections. Do not infer native pointer ownership, sandboxing or executed tests from a docs-only fix list. No claim here depends on excluded old Nukkit evidence.
