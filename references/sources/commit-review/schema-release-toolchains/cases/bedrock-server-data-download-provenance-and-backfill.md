# A plausible download URL is not artifact identity {#b2-a-plausible-download-url-is-not-artifact-identity}

## A review-to-implementation chain with distinct credit {#a-review-to-implementation-chain-with-distinct-credit}

Purple/purple-blog submitted PR #3 to fill missing Linux `1.26.10.22` preview data after the artifact reportedly appeared later upstream. The patch contained a Linux URL but copied the Windows SHA256. The target requested changes, reported downloading Linux separately, supplied its distinct digest and a PowerShell reproduction command, then closed the PR intentionally to apply the correction directly.

The captured complete thread and existing [thread dossier](../../../thread-review/threads/EndstoneMC--bedrock-server-data--pr-3.md) distinguish contributor discovery, submitted mistake, review objection and supersession. The direct correction commits exactly the digest in the review; machine-checked identity proof connects them. The PR's captured `merged=false` is preserved. The review is source-reported hash computation; Neither binary was fetched or hashed.

The narrow portable lesson is strong: each platform artifact needs its own identity measurement. Different URLs do not justify copying a digest, and a valid 64-hex shape does not prove the file it names. A collaborator's proposal should not be reattributed wholesale to the integrator, nor should a closed unmerged PR erase its role in the eventual fix.

## Transport evolution {#transport-evolution}

The original scraper downloads via streaming requests, but hashes by reading the completed file into memory. It has neither explicit request timeout nor HTTP-status rejection. `ee9a3056ecae3d7b18e486cc8af621b9e27c028b`, titled “resolve timeout,” adds a browser-like User-Agent and URL logging. It changes request presentation; it does not bound waiting time.

`614d1bd6ed0dec7a3116f1bfe0b7a5acdf758bf6` uses the official Minecraft services download-links API and Pydantic aliases for `downloadType`/`downloadUrl`. The enum knows four Bedrock variants plus Java serverJar; Java is filtered after validation. Benefits: less dependence on HTML markup and explicit URL/type structure. Costs: a future unknown enum type can reject the whole response before filtering, duplicate kinds overwrite in a dictionary, and removal of the earlier per-platform exception loop changes failure isolation. HTTP status is checked for the API response, but binary GET status remains unchecked until the final target.

## Heuristic backfill is a candidate generator {#heuristic-backfill-is-a-candidate-generator}

The final patch adds binary `raise_for_status` and missing-platform backfill:

1. Scan release/preview directories and parse metadata.
2. Skip complete pairs and warn/skip empty records.
3. Derive another platform's path by replacing preview variants before generic release variants.
4. Resolve the channel/platform enum.
5. HEAD the candidate with redirects; require status 200.
6. Invoke the normal download/hash/write path and log success or per-candidate exception.

The ordering avoids accidentally turning a preview path into a wrong release-like partial substitution. It remains heuristic: releases can use different build revisions, archive paths can change, HEAD can be unsupported or redirected, and a successful response may contain an error page. GET status rejection fixes one concrete earlier weakness; it does not validate archive contents, publisher signatures, release identity, version metadata or response body length.

Some errors still bypass per-candidate handling. JSON parsing, accessing the existing URL, derivation and enum resolution occur outside its `try`. Earlier API/latest processing happens before backfill and can abort the run. No request timeout is added. Multi-file state publication is not atomic. The context snapshot still has one missing Linux entry, so the presence of a backfill implementation is not evidence it executed successfully.

## Tests warranted by the mechanism {#tests-warranted-by-the-mechanism}

Proposed, not executed: all four release/preview swaps; no recognized path; asymmetric archive revision; 404 HEAD; HEAD 405 with successful GET; redirect to nonarchive content; bad JSON; unknown API kind; one failed platform followed by a good one; incomplete download; historical unindexed version not becoming latest; an interruption between metadata and registry writes. For authenticity-sensitive consumers, distinguish “observed digest of content we fetched” from “publisher-authenticated expected digest.”

Use this case for package mirrors, schema registries and release metadata ingestion. Do not generalize it into permission to run vendor binaries or trust any URL that looks official.
