# Version, channel and platform identity must survive schema migrations {#b1-version-channel-and-platform-identity-must-survive-schema-migrations}

## Original failure surface {#original-failure-surface}

The first updater (`beb02ac6f6f1cb84e9cb331ae5e769bd9c465bc5`) scrapes Windows and Linux URLs independently, but derives the shared aggregate key from Windows and writes both artifacts under it. This assumes upstream releases are synchronized. The generic-titled `ea5c39a4f6f59603fbdbe5c6c4e7d593cb4c9199` deletes a record that violates that assumption: Windows `1.21.50.07` was paired with Linux `1.21.44.01` under key `1.21.50`. The message does not explain the deletion; its significance is inferred from the complete payload.

Aggregate validation parses 20 relevant before/after snapshots. It detects exactly that mismatch in the before snapshot, while validating key/URL agreement, platform names and digest shapes throughout. That is exhaustive structural checking of these payloads, not independent retrieval of vendor binaries or a claim that each digest's literal digits express a new engineering decision.

## Schema changes are API changes {#schema-changes-are-api-changes}

The first migration (`39834eb2c2ee9b3ba94aaa9358ebf14f05af01d3`) wraps all eight original versions under `binary`; the audit proves the nested mapping is equal. However, the old existing-version guard still tests membership in the top-level object. Writers/loaders were updated, but the reader of that key was missed. This is a useful migration counterexample: equivalent data values do not guarantee all access paths changed.

The `docs(v2)` commit `6c8293caaed723747d14ed4b1c23c5803a00cc65` deletes the old workflow/updater/requirements and all 33 accumulated version records, not just documentation. The new README initially promises channel/version directories, extracted artifacts and latest links. Those promises are not all implemented. Later `50f6581462b058d8377de23966fafa316b35778d` removes the phantom artifacts/links and describes metadata only. Do not infer old records were migrated by a deletion-only commit or that promised symlinks existed.

## Independent platform updates {#independent-platform-updates}

The v2 updater (`6bebb5bd545a8ac4b8f44b202473debad26effe0`) derives a key from each platform URL, keeps release and preview channels separate, and updates one platform within existing version metadata. This permits Windows and Linux to arrive at different times without falsely merging different versions. Later manual additions for release 1.21.110 Windows and 1.21.111 Linux are concrete platform-completion cases.

The registry (`c107755a46d90c1ef0d85bb08ae7882ac1c9d8e9`) tracks latest plus ordered versions. Inserting a newly observed version at the head is suitable only when observation order tracks release order. Historical discovery breaks that equivalence. A later call that adds an unindexed old version can make it latest unless registry ordering is handled separately. In contrast, Purple's historical preview `.23` contribution was inserted below `.24/.25`, preserving latest; target integration later also preserves `.26`. That exact preservation is proved here.

## Three concrete identity-preserving transformations {#three-concrete-identity-preserving-transformations}

Full proofs, alongside all exact before/after leaves in JSON deltas:

- `11aad100297b3a66732d7eff0e59dcae1a16428c`: renames `checksum` to `sha256` in two records without changing four digest values or any URL/version. This names the algorithm; it does not recalculate hashes.
- `62c2778c6e1160fd24b23b95a9f3b67fec1de89e`: stable→release path move has the exact same blob `d769f35ec2bc8bc18784547982f3688f4655ddda`. The enum/registry rename occurred earlier, exposing intermediate path skew.
- `28d69641f7aaede3a80ab771dff584a2aa2f36f1`: three beta→preview folders and internal versions are transformed consistently, with unchanged URLs/hashes. Registry names also change. Existing consumers of old paths get no compatibility aliases from this diff.

## Integration and final snapshot boundaries {#integration-and-final-snapshot-boundaries}

Four merges were reviewed against both parents. The 2024 origin/main integration is exactly a union of parent JSON mappings; the new version came through an automatically committed data record. Purple/purple-blog authored incoming historical/missing-platform data; the target integrated it. Dependabot authored a later action update. Context messages/parents and all six contextual commits prevent blanket merge authorship.

At target tip `a570c947cbe8860e339ab244f999f7d66d972675`, the contextual structural check covers all 95 metadata files: names/versions/URLs agree, registry and files are mutually reachable, latest is the first entry, and no complete pair shares a digest. One record, release `1.26.11`, still lacks Linux. These 95 files are contextual snapshot coverage, not 95 additional reviewed commits. A missing platform can be valid unavailable data; do not fabricate it to make a symmetry check pass.

## Offline decision exercise {#offline-decision-exercise}

If a supplier exposes Windows version B while Linux remains version A, record them independently or leave B/Linux absent; never reuse A's URL/hash under B. If migrating field/path names, enumerate every consumer access path and verify transformed values plus reachability. If backfilling historical data, assert that latest does not regress. The reviewed source establishes why these checks matter; no upstream downloader or vendor server was run.
