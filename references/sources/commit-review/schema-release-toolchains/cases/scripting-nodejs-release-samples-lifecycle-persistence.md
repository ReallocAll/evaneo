# Runnable-looking samples still need lifecycle and durability boundaries {#n2-runnable-looking-samples-still-need-lifecycle-and-durability-boundaries}

## Scope and packaging {#scope-and-packaging}

Eight sample packs are present at the final selected commit. Structural audit parses every manifest, confirms unique header/module UUIDs and existing script entrypoints, and records API versions. Seven use `@minecraft/server` 2.4.2; Discord requests beta. Two npm manifests use semver ranges (dayjs and discord.js), not a reproducibly locked dependency tree. These checks establish package structure, not that any pack ran or each dependency version is compatible.

The documented runtime gives packs full capabilities of the server user: filesystem, networking and child processes. Ignoring npm lifecycle scripts does not sandbox the code imported afterward. The sample commands and URLs are research data; no packages were installed, server opened or token entered.

## Filesystem example: API demonstration versus durability {#filesystem-example-api-demonstration-versus-durability}

`7d629a3c...` loads a JSON visits map once and asynchronously writes updated state after initial spawn. ENOENT is intentionally an empty first run. Other parse/read errors log and also produce an empty map, so a subsequent write can destroy corrupt-but-recoverable history. Multiple fire-and-forget writes lack serialization; invocation order does not guarantee filesystem completion order. There is no temporary-file/rename protocol or recovery version.

`4e76eb55...` moves all sample persistence into `pack_data` rather than the server's reserved `data` tree. Relative `node:fs` paths are anchored at the server working directory. This is a concrete data-ownership clarification: pack updates should not replace durable data, and sample storage should not collide with server-owned paths. It is not a durability guarantee.

For important state, proposed tests include concurrent updates, write failure, malformed previous data, restart during write and recovery without silent reset. Those tests were not run here.

## SQLite example: batching has a failure policy {#sqlite-example-batching-has-a-failure-policy}

`53d03660...` normalizes action into one table, uses a composite primary key and prepared upsert, and batches in-memory increments into a 100-tick transaction. WAL and prepared statements are explicit choices; no throughput measurement accompanies them. DatabaseSync still executes synchronously on the server thread, although batching reduces per-event database work.

The flush copies and clears pending state before beginning/committing. On failure, rollback logs the error but does not return the batch to pending; a failed flush loses counts. BEGIN itself is outside the try. The README's crash window is therefore not the whole loss model. A robust design must decide whether to requeue, stop, retry with bounded backoff, or explicitly accept loss, avoiding double-counting if commit outcome is uncertain. These are inferred trade-offs from source ordering, not claims of observed production corruption.

## Worker example: retain the cross-thread boundary {#worker-example-retain-the-cross-thread-boundary}

`0e6d4622...` isolates maze search from Script API calls. The worker generates candidates by seeded randomized depth-first search, computes paths by BFS, picks a strong candidate and transfers a byte-grid buffer. The main thread handles player/world operations and spreads construction with `system.runJob`. Width and attempts are clamped; unlimited repeated requests can still create concurrent workers.

`368ebee2...` is titled as comment cleanup but renames maze.js→maze.mjs with byte-identical content, while leaving main's old filename until `790a8e0f...`. That follow-on also replaces `new URL(..., import.meta.url)` logic with `node:path` because this runtime exposes a relative filesystem path rather than a file URL. It permits console search without building, checks player validity before constructing and uses the system tick count directly.

Initial docs queue worker messages to a tick interval. Later code handles results directly under the documented event-loop integration, while the actual worker still never calls Minecraft API. Do not turn that callback change into permission to touch game state from arbitrary worker threads. The docs' worker timings are removed rather than treated as universal overhead guarantees.

## Networking examples: bound state, not just work per callback {#networking-examples-bound-state-not-just-work-per-callback}

Discord's before-chat callback only enqueues strings and periodic flush batches under a character limit. This reduces callback cost but does not bound queue growth. The subscription remains when disabled; the take routine has no branch to consume a leading line larger than its limit (real platform message-size constraints were not tested); send failure loses dequeued lines. It correctly separates markdown escaping from mention control: sends explicitly set `allowedMentions: { parse: [] }`. Configuration keeps the token outside the pack code, but is not an encryption or access-control mechanism.

The HTTP sample binds loopback `127.0.0.1:8787`, handles GET /status and publishes a once-per-20-tick plain-data snapshot. That separates collection of live game data from serving requests. Snapshot freshness, network resource costs and player-name disclosure remain relevant if an operator deliberately exposes it. Localhost default is a narrower audience than public binding; The service was not opened.

## Identity and sampled persistence {#identity-and-sampled-persistence}

The seen command stores last-seen timestamps in dynamic properties by lowercased player name, refreshes at spawn/leave and 1200 ticks, and uses dayjs for relative wording. Names are not immutable player identity; renames split history. “One minute” assumes normal tick progress and does not establish disk-flush durability. The command's Any permission suits this demonstration, not every deployment.

## Offline use {#offline-use}

Choose the sample by mechanism, then add the relevant contract: durable file writes, transaction retry semantics, worker admission limits, queue capacity/retry/oversized-message policy, HTTP audience and immutable identity. Copying the sample without those decisions is not evidence-backed production engineering.
