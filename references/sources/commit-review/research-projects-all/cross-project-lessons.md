# Scoped cross-project lessons {#scoped-cross-project-lessons}

These evidence-backed engineering aids each have an applicability boundary and counterexample; they are not universal prescriptions. The teaching repository contributes no independent C++/Python implementation evidence.

## 1. Port the whole contract, not only the syntax {#1-port-the-whole-contract-not-only-the-syntax}

Lanelet2x's ROS removal requires component dependencies, exported names, runtime DLLs, fixture resources, installed-consumer examples and Python module naming to move together. DynOMo's shell replacement requires interpreter identity, current directory, archive layout, download failure semantics and keep-list normalization. In both cases, the meaningful work is at boundaries between subsystems.

Apply when removing an ambient framework or moving a Python research pipeline across operating systems. Inventory those assumptions explicitly. Counterexample: replacing mkdtemp with an ordinary fixed path preserves a superficially similar API use but loses uniqueness; creating an archive destination too early changes shutil.move layout. See [build case](cases/lanelet2x-standalone-build.md) and [data case](cases/dynomo-portability-and-data.md).

## 2. Separate package metadata from runtime compatibility {#2-separate-package-metadata-from-runtime-compatibility}

Lanelet2x's SOABI modules and runtime-library staging solve different pieces of a wheel. The CUDA rasterizer additionally depends on the installed Torch/CUDA/compiler/hardware contract, while Linux repair deliberately leaves Torch libraries external. A wheel filename alone cannot encode or prove that whole contract.

Apply to native Python packaging and “installs but cannot import” diagnosis. Counterexample: a valid CPython/platform tag says nothing about absent external Torch libraries or unintended build-tree RPATH dependence. The files contain configuration and compatibility intent, not passing deployment evidence. See [CUDA wheel case](cases/rasterizer-wheel-contract.md).

## 3. Preserve graph reachability when changing linkage {#3-preserve-graph-reachability-when-changing-linkage}

Lanelet2x moves built-in registrars into factory translation units so using the factory also references implementations in static archives. A registry can be correct as a data structure while missing at runtime because its object file was never included.

Apply to C++ static plugin/factory patterns. Counterexample: custom plugins in separate static archives still need an explicit registration/reachability strategy; centralizing all built-ins increases coupling and does not prove every LTO configuration. The shared Boost dependency also means static Lanelet2 is not a fully static program. See [linkage case](cases/lanelet2x-linkage-and-tests.md).

## 4. Treat tensor device and gradient contracts separately {#4-treat-tensor-device-and-gradient-contracts-separately}

DynOMo's CPU history selection needs a compatible mask device. The rasterizer's returned auxiliary tensors have a separate backward contract; depth is explicitly not differentiated through that output. Fixing an indexing mismatch does not validate numerical accuracy or optimize the pipeline.

Apply to Python/CUDA boundaries and stored historical state. Counterexample: moving every mask to CPU may add transfers; an auxiliary depth loss may require a different differentiable route even though depth values are returned. See [device case](cases/dynomo-device-and-research-limits.md).

## 5. Preserve reversals and failed intermediate assumptions {#5-preserve-reversals-and-failed-intermediate-assumptions}

Ninja is forced and relaxed on Windows; std::filesystem is attempted and reverted for C++14; fixture state moves twice with a focused follow-up fix. DynOMo dependencies are simplified then filled in and pinned. A single attractive commit title is insufficient for a final recommendation.

Apply when deriving reusable guidance from history. Counterexample: “always use Ninja,” “always modernize filesystem APIs” and “unpin research environments for portability” each conflict with part of this actual sequence. Prefer the final boundary and its costs, keeping explicit reasons distinct from inferred ones.

## 6. Keep source contribution, integration and validation separate {#6-keep-source-contribution-integration-and-validation-separate}

The Geocentric fix's final blobs match Michał Antkiewicz's upstream commit. Rasterizer methods and depth extensions are credited by upstream headers/README. Teaching merges integrate participant work. Build workflows and badges describe intended validation but do not prove it happened successfully.

Apply to engineering evidence review, fork maintenance and agent-written summaries. Counterexample: GitHub author attribution for an import, large merge patch size, or a release-labelled commit cannot establish the originality of an integrated algorithm or runtime correctness. Exact tree/blob/patch identity permits efficient deduplication while preserving per-SHA identity. See [attribution case](cases/lanelet2x-attribution-and-release.md).

## Demand navigation {#demand-navigation}

- Dependency and attribution review: environment tradeoffs, upstream licensing notices and algorithm credit
- Initialization/configuration: Conan/CMake setup and explicit subprocess roots/interpreters
- Architecture/API: component graph, factory registration, Python binding/module names and autograd contracts
- Implementation/refactoring: compiler guards, import-safe CLI cleanup, masking and path normalization
- C++/Python boundary: SOABI, Boost.Python, Torch CUDAExtension and external runtime ABI
- Concurrency/lifecycle: fixed temporary-directory counterexample and stored-state device boundaries; not a general concurrency-design study
- Diagnosis/testing: static-factory missing registrations, fixture roots, removed import smoke checks and configuration-versus-results distinction
- Profiling/optimization: no measured performance result; CPU copy costs and kernel contributor caps are considerations only
- Persistence/recovery: partial downloads and archive layout, not a verified crash-consistent storage implementation
- Build/CI/deployment: static/shared matrix, wheel repair, packaged-consumer tests, Docker tradeoffs
- Documentation/review: scoped authorship, merge context and submission templates, with teaching code claims excluded

No claim is made that these four histories cover every demand family deeply or that they demonstrate native ABI hooks, broad concurrency expertise, or measured optimization. Gaps require additional publicly verifiable evidence, not extrapolation from these examples.
