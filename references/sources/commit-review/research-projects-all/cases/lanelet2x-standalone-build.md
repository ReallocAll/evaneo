# Lanelet2x: extracting a C++ library from its ROS build environment {#lanelet2x-extracting-a-c-library-from-its-ros-build-environment}

## Decision and provenance {#decision-and-provenance}

The selected 56-commit 2023 sequence is chiefly a standalone-distribution project. The final README calls Lanelet2x a fork with ROS1, ROS2 and Catkin dependencies removed. The existing map model, routing, matching, projections, regulatory elements and Boost.Python APIs are upstream work. The fork's contributions should be described as build-system, portability, package and integration engineering, with focused implementation repairs where the diff supports them.

Start with 600296e, then 2e457ee, the IO/projection/traffic/routing/validation/matching stages in [the chronological ledger](../lanelet2x-review.md), and final Conan recipe, root CMake, Python CMake, pyproject, and Python initializer. Public provenance: [initial commit](https://github.com/wu-vincent/lanelet2x/commit/600296edffeaaed4209c10221da6c2e4456a9522).

## Mechanism and sequence {#mechanism-and-sequence}

The initial migration introduces Conan 2's generated dependency/toolchain files and a plain CMake root; only core is enabled at first. Modules are brought back incrementally, with explicit native dependencies and tests. Removing the ROS package manifests and custom build files later is a separate cleanup step. This ordering matters: the first commit is not a complete working standalone distribution merely because its title says Conan 2/plain CMake.

The final recipe names the C++ package `lanelet2`; Python metadata names the distribution `lanelet2x` while import modules remain `lanelet2`. Conan components map to CMake names such as `lanelet2::core`. Component relationships reconstruct the native graph: IO and traffic-rules depend on core; projection adds IO; routing adds traffic-rules; matching adds IO/projection/traffic-rules; validation adds routing as well. External requirements include Boost 1.75–1.81, Eigen 3.4.0, GeographicLib 1.52 and pugixml 1.13. GTest is declared for tests. These are the recorded versions, not a recommendation that they are current today.

Python packaging compiles each existing binding source as a MODULE with SOABI and a compile-time module name, then installs into the import package during SKBUILD. It links Boost.Python and the native component set. The source list is initially globbed from the wrong directory and corrected in the next commit. A version lookup that temporarily imports the native package is subsequently replaced with a literal recipe version and scikit-build regex metadata. That avoids requiring an already-built extension just to determine the build version.

Runtime library discovery differs by platform. Windows uses `TARGET_RUNTIME_DLLS` and packages dependent DLLs in `bin`; the Python initializer adds that directory to loader search/PATH and auto-imports submodules. Linux/macOS stage shared libraries in a source-tree `build/lib` directory for auditwheel/delocate to find. CMake's absolute staging RPATH is therefore an intermediate repair input. It is not itself proof that the final wheel is relocatable. macOS adds `@loader_path` RPATHs to staged Boost dylibs. Several commits change the staging root, showing a real coordination problem between recipe layout, CMake install paths and repair tooling.

## Alternatives and reversals {#alternatives-and-reversals}

- Ninja is initially forced everywhere; Windows later returns to a multi-configuration generator/preset. The relevant principle is matching toolchain assumptions, not insisting on one generator.
- Explicit SHARED targets initially defeat the Conan static/shared option; later `add_library` respects `BUILD_SHARED_LIBS` and Conan advertises `-static` filenames when appropriate.
- Conan defaults eventually become static while Python wheel prebuilds explicitly request shared. Boost remains configured shared, so “static Lanelet2” does not mean a fully static dependency closure.
- A move from Boost.Filesystem to `std::filesystem` is reverted alongside C++14 restoration. This history supports retaining a compatible baseline when a modernization changes required language/runtime assumptions; it does not prove the newer API is intrinsically unsuitable.
- Native installation later excludes several resources/docs/scripts. Minimal install output trades away bundled example maps; consumers must not assume ROS-era resource locations remain available.

## Tests, limits and costs {#tests-limits-and-costs}

Configured coverage includes CTest/GTest, three-OS Conan package creation, and cibuildwheel tests of the installed binding package and Python examples. The release preparation adds a separate Conan consumer example that links the packaged targets. These are valuable distinctions: building inside the source tree can hide missing exports, while consuming a package tests a different interface. No workflow logs, passing test results, actual wheels installed by this review, or Windows/macOS runtime checks were obtained.

The final CMake uses `NOT BUILD_TESTING STREQUAL OFF`; values such as `0` or `FALSE` deserve checking rather than assuming canonical CMake boolean semantics. `set(CMAKE_CXX_STANDARD_REQUIRED)` has no value in the viewed root. Python discovery uses the `Python` package but retains a `Python3_INCLUDE_DIRS` reference. Imported targets may supply requirements, but source inspection alone does not establish every configuration is valid. These are focused review questions, not reproduced failures.

## When to reuse {#when-to-reuse}

Use this case for “remove a framework build dependency,” “package a native C++/Python library,” “why does a wheel import locally but fail elsewhere,” or “split C++ consumer and Python distribution linkage.” Build a graph of components, compile features, dependencies, exports, runtime libraries and test resources. Verify both source-build and installed-consumer contracts. A proposed test plan should cover a clean consumer, alternate working directory, static/shared mode, Python minor versions, and a machine without the build-tree libraries.

Do not reuse it as evidence that all projects should remove ROS, use Conan, use static libraries, auto-import all Python modules, or prefer C++14 indefinitely. In a ROS-native application its integration facilities may be the right boundary. Packaging configuration and author-reported availability remain separate from measured portability.
