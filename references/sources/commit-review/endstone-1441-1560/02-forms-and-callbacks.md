# Forms: from wire schema to callbacks and lifecycle guards {#forms-from-wire-schema-to-callbacks-and-lifecycle-guards}

## Initial capability and schema corrections {#initial-capability-and-schema-corrections}

Forms are built in small consecutive stages. [1463](https://github.com/EndstoneMC/endstone/commit/9b3a46c41a90a3688ddf9e3b3304481ad6e03b54) introduces event models and a coordinator hook, but the wrapper handlers initially do nothing. [1464](https://github.com/EndstoneMC/endstone/commit/b265efe95dbf241d48e5c06b8b25b250eee89976) supplies conversion from the native JSON model to nlohmann JSON. [1465](https://github.com/EndstoneMC/endstone/commit/07e610e8d8d952849a47e5591fa3006c4f04d7a7) sends the two-button MessageForm using the protocol's modal type; [1466](https://github.com/EndstoneMC/endstone/commit/d0e3f19a8442f0ce7c9482e9d5c0bbfbcd728b24) makes construction and Python exposure usable, and [1467](https://github.com/EndstoneMC/endstone/commit/d14d2209bdcbf5b7990146f4c7b5767fbe16c791) corrects translated text to rawtext. The public name “ModalForm” introduced later refers to custom_form on the wire. Keeping these names distinct avoids importing the wrong protocol shape into a future implementation.

[1469](https://github.com/EndstoneMC/endstone/commit/bf3b5d90a6ced930f6658c1f405a1b2c75f6abdb) changes a global counter into per-player state and stores form variants before sending. Unknown response IDs are deliberately ignored at [1470](https://github.com/EndstoneMC/endstone/commit/639d96a5d2ca6ce8d6515b6559c46db2ce4739c2), with comments explaining coexistence with Script API forms. A counter starting at 0xffff is a collision-avoidance heuristic, not a demonstrated shared allocator. ActionForm introduces button lists and URL/path icon selection. The Message derived-variant experiment is replaced by a type alias in [1471](https://github.com/EndstoneMC/endstone/commit/9b8235cc2bd808b7454ee1b0dbc92f8d331ac620). These are observed alternatives, not evidence of a general aversion to inheritance.

[1485](https://github.com/EndstoneMC/endstone/commit/969f6ec1118c12a1fc411045d722322e0093a2d6) replaces one serializer visitor with per-type template specializations, making controls easier to add without one large header visitor. Toggle, ModalForm, Label, Slider, Dropdown, StepSlider and TextInput follow. The history preserves real mistakes: custom-form content starts as text before being appended to, Toggle misses its text field, StepSlider uses options instead of steps, and TextInput's default is initially serialized as a translated message. [1488](https://github.com/EndstoneMC/endstone/commit/e0bc4ab5756076eaab14f16019d41379c60e2b80) and [1498](https://github.com/EndstoneMC/endstone/commit/49069d5daf9b106fd23cb86533b025d9b86755f4) repair these concrete shapes. Button becomes nested in ActionForm, while Python StepSlider eventually has an independent explicit class surface even though the C++ class still derives from Dropdown.

This sequence supports keeping serialization behavior testable independently from builders and bindings. It does not establish that such tests existed here. Public module exports and stubs sometimes lag implementation by a commit; source inspection must distinguish the actual language surface at each SHA.

## Native JSON fidelity and the response boundary {#native-json-fidelity-and-the-response-boundary}

[1489](https://github.com/EndstoneMC/endstone/commit/63457d8faa69d335e4b2246998afc14c30438d41) corrects the native array representation to a vector of pointers. The commit title expresses frustration with Mojang, but no external code comparison or issue evidence was read in this workunit. The locally supported claim is a representation correction. The converter also leaves empty arrays and objects as null, because it begins with a null result and only changes type when values are added.

Submit callbacks start with a restricted bool/int/string vector for custom forms at [1492](https://github.com/EndstoneMC/endstone/commit/2341bb10fad7166cce172dce0e1cf50c838d55c8) and are dispatched at [1493](https://github.com/EndstoneMC/endstone/commit/3b2c4993bc433dc67762946edf0878597e82e1bf). That representation loses fractional numeric values and cannot represent null label placeholders. [1502](https://github.com/EndstoneMC/endstone/commit/a2a5c75abf3ac18dddd53b7496202fe8344f1447) returns a JSON string instead. The commit does not explain its motivation beyond the change; preserving those values and delegating interpretation is an inference grounded in the before/after code. It shifts work to plugin authors rather than designing a richer stable result type. That tradeoff is worth retaining, without presenting it as the only correct API design.

MessageForm maps a boolean to button zero or one. ActionForm reads an integer. Known responses are dispatched and then removed; unknown forms remain untouched. std::exception is logged around callback invocation, and temporary debug printing is removed. The form map owns the value and callback, but that alone does not make nested callback actions safe.

## Python binding and ownership corrections {#python-binding-and-ownership-corrections}

Close callbacks first take Player&, then Player* in [1491](https://github.com/EndstoneMC/endstone/commit/1b592e37b303dce44155b580147138d668a4a273), whose title reports that they now work. The binding order is adjusted to register Player/Mob types before signatures refer to them, and callback aliases make defaults consistent. These observations support a boundary-specific repair, not a blanket rule that pointers should replace references in C++ APIs. No pybind implementation or external callback issue was audited here.

[1515](https://github.com/EndstoneMC/endstone/commit/857b039a6d1ab46355a588c05b43d33a01e9d21b) adds button click callbacks through a default ActionForm submit lambda capturing this. Full endpoint source shows forms are copied/moved into a variant and stored by value; no custom copy/move operation rebinds that capture. The Python constructor also unconditionally calls setOnSubmit, and its default is empty, overwriting the default dispatcher. Those are direct counterexamples to treating the form value model as fully safe callback composition. A future design might dispatch from the stored form rather than capture the builder, but that is a reviewer-derived alternative, not an alternative discussed in the commits.

Optional getters and setters also do not always share the same domain: button icons can be absent but the setter accepts only a string. Controls return collections by value or through STL binding conversion, so the source does not justify promising live Python list editing. These limits are small but relevant when translating an API across languages.

## Death and closure semantics {#death-and-closure-semantics}

The initial coordinator hook resolves a weak player and dereferences it. [1503](https://github.com/EndstoneMC/endstone/commit/53292ddae639b5051f8195b4d1b5645888a90bd5) adds the specific missing-player guard for submissions after death. [1504](https://github.com/EndstoneMC/endstone/commit/c01f78f00cded7b24174731baf987113768a3601) introduces closeForm, sends a native close packet, and clears tracked forms before the death event. [1506](https://github.com/EndstoneMC/endstone/commit/739abdd7af337c7ea9198bbf12915f0160923658) rejects sends to dead players and skips callbacks for dead players while removing their tracked entries. These are layered repairs: weak lookup, client closure and callback liveness are distinct.

Programmatic closeForm clears forms without firing their close callbacks. Callback handlers invoke the callback before erasing their iterator, so a callback that calls closeForm can invalidate the current entry. This was established by reading the complete endpoint player source; no crash reproduction was run. The code still dereferences the weak registry before the player null check. The research should preserve the concrete repaired case and the remaining bounds, rather than upgrade a “fixed crash” title into global lifecycle safety.

## Outcomes and applicability {#outcomes-and-applicability}

The roadmap marks forms delivered in 0.5.0 while release notes call the API experimental. Titles saying controls or callbacks work are author-reported outcomes, not measurements from this review. No dedicated form behavior tests are added in this commit sequence. The strongest reusable evidence is the iterative alignment of native events, ownership, wire shape, callbacks and language bindings, with explicit revisions at each boundary. It is useful for API design, adapter debugging and deciding which integration seams need tests. It is unsuitable as a claim that any present-day form behavior is unchanged.
