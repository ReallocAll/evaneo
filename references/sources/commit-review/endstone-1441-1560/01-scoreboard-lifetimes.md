# Scoreboards: side effects, borrowed wrappers and changing owners {#scoreboards-side-effects-borrowed-wrappers-and-changing-owners}

## Decision chain and why the order matters {#decision-chain-and-why-the-order-matters}

The previous unit ended with an exposed but incompletely implemented Scoreboard family. This unit begins by repairing the wrapper layer, then supplies native registration and identity bookkeeping, and finally creates independently owned boards for individual players. It is not one timeless ownership policy. The chain is a direct parent sequence, so the intermediate inconsistencies and repairs are causal, rather than merely adjacent timestamps.

A Score initially depended on the caller's Objective wrapper. [1442](https://github.com/EndstoneMC/endstone/commit/6e84879205bf34e70e20c851ee3d9859d16d1069) gives the Score a unique copy of that wrapper. The distinction is crucial: the copied wrapper retains references to the same native objective and board. Unique ownership solves the wrapper allocation's lifetime, not the referenced native graph. Public creation becomes useful through native addObjective in [1448](https://github.com/EndstoneMC/endstone/commit/a1b20e010e9ed1e091099eb3ae7385e79cf6cebf), core registration in [1449](https://github.com/EndstoneMC/endstone/commit/48b79e92c8d26d7adcdc541b4f2d9207a862f405), access/list operations in [1450](https://github.com/EndstoneMC/endstone/commit/9cb4793d0097ff02043ea5b96f5889548e04cbcd), and Server exposure in [1456](https://github.com/EndstoneMC/endstone/commit/fb3def767559b455524f1940d56d29ed9ecdae08). Those implementation dates supersede a claim that the preceding interface-only commits already delivered working registration.

The mutation pipeline is particularly informative. [1457](https://github.com/EndstoneMC/endstone/commit/5c0a9867ab5bcbb79cc823482060f090f08e8d64) creates a native identity when setting a previously absent entry, while reads remain lookup-only. [1458](https://github.com/EndstoneMC/endstone/commit/88de7d212212736b6b8e824b94585270df8633c6) models validity separately from the integer. [1459](https://github.com/EndstoneMC/endstone/commit/ffde241a3b0c67ec49b077f11958a1466156beac) then performs writes through the identity reference, increments the reference count only for the first successful assignment, and calls onScoreChanged only on success. The alternative actually observed in the history is a direct score-map update with insufficient surrounding bookkeeping. The later path acknowledges that writing the value and maintaining engine participation are separate responsibilities. This is good evidence for following the native side-effect boundary in this case; it is not proof that every wrapper operation in the project follows it.

## Removal and non-owner representation {#removal-and-non-owner-representation}

[1443](https://github.com/EndstoneMC/endstone/commit/6e45651c000671fe24e26baecce6c6946cdc0ef8) implements unregister and replaces a fake enum sentinel with an optional display slot. Its removal path calls onObjectiveRemoved, erases the owning map entry and cleans display entries. It does not itself explicitly remove the hashed lookup. Native notification behavior may perform additional work, so the absence of a local erase is a limit on what is proven, not enough to assert a live stale-map bug.

The explicit crash claim in [1499](https://github.com/EndstoneMC/endstone/commit/81a70494a20c037f86b1c578f7716affce1264b2) points to the modeled NonOwnerPointer. Its old shared_ptr directly owned a native object already owned elsewhere. The replacement shares a control block whose target is raw. [1501](https://github.com/EndstoneMC/endstone/commit/7287c3e9381ca46fbb7a694b4c718d86ffd865e4) adds reset during destruction. [1516](https://github.com/EndstoneMC/endstone/commit/39491a290bfa44a431c21f1cfb7425f529f3ed49) separately corrects GameSession to own its network handler and synthesize a non-owner handle on demand; [1517](https://github.com/EndstoneMC/endstone/commit/64a4c35a2bfcb867bb11c6f37741e54476217820) types the control-block pointer as its base class, enabling a derived-pointer adjustment instead of a void-pointer reinterpretation. The max-player failure is reported fixed by that latter change. This is a useful cross-subsystem diagnostic chain: a foundational pointer model can explain failures far from scoreboards, but the supplied code does not prove every external failure report's exact root cause.

There are important counterexamples. At the endpoint the modeled owner destructor is defaulted and does not explicitly null the control-block target. Accessors throw on empty/dangling state even though several public operators are noexcept, and reset can throw from the destructor. Therefore the safe inference is that the implementation stopped mistakenly owning its target; calling it a completed safe weak-reference abstraction would exceed the evidence.

## Custom boards: a dated ownership reversal {#custom-boards-a-dated-ownership-reversal}

The primary board is documented as persisted, affected by /scoreboard and used by default in [1539](https://github.com/EndstoneMC/endstone/commit/1bf454f44a45663e0f7c3fe0c31d4881e651463b). [1544](https://github.com/EndstoneMC/endstone/commit/e93ecbae7194f63972d10c1b38a6c49bb9cd5fb4) adds custom native boards without LevelStorage. The wrapper owns that new native object, while the server initially owns every wrapper in a vector and returns raw pointers. [1545](https://github.com/EndstoneMC/endstone/commit/aaa6380886c3767d5a0367f03d69f71c8a31983f) changes the contract immediately: return shared_ptr, hold only weak references in the registry, and use a shared Python holder. [1546](https://github.com/EndstoneMC/endstone/commit/486686a9605ad90780b850c494563c0baf89c64f) retains boards strongly while players are assigned to them and removes the assignment at player destruction. [1547](https://github.com/EndstoneMC/endstone/commit/0d5fa684a739094a6a93b0b4e183316604cd4558) recovers shared ownership through shared_from_this when accepting a public Scoreboard reference.

This is concrete evidence of adjusting ownership to the consumer graph, with a counterexample to any simplistic “always use unique_ptr” or “the server owns everything” summary. The primary wrapper still borrows an engine-owned board; a custom wrapper owns its native board. Objective wrappers still borrow both. The source does not make an Objective keep its custom Scoreboard alive, nor does checkState compare native identity when a removed name is recreated. A native-address equality operator in [1501](https://github.com/EndstoneMC/endstone/commit/7287c3e9381ca46fbb7a694b4c718d86ffd865e4) solves wrapper equality, not lifetime validation.

Association alone does not display data. [1546](https://github.com/EndstoneMC/endstone/commit/486686a9605ad90780b850c494563c0baf89c64f) openly leaves packet work pending. [1548](https://github.com/EndstoneMC/endstone/commit/dd2a2f9ce772186819eb69132a5361362f6dab8e) resets the player's old-board scores, which is actual data mutation rather than a pure viewer-unsubscribe operation. [1557](https://github.com/EndstoneMC/endstone/commit/fce2d8cf9840f0489cfd4cd22d2f23c30f7b0aa5) supplies the packet sender and calls native onPlayerJoined before updating tracking. Its title reports that custom boards now display; no running client capture or test result was produced in this review. The Linux construction chain is analyzed in the native-factory dossier.

## Endpoint contracts, costs and reuse limits {#endpoint-contracts-costs-and-reuse-limits}

Full endpoint source still accepts render_type without using it, logs that setRenderType is unsupported, and drops a supplied display name in the three-argument overload. getScores returns wrappers for all objectives; isScoreSet distinguishes absence. getEntries only resolves online players/current actors and performs repeated scans. These are bounded observations that constrain API reuse, not an unbounded defect hunt. No performance measurements were found in these commits.

The unit changes mock signatures but introduces no behavioral scoreboard tests. C++/Python ownership policy, native container bookkeeping, UI notification, persistence and wrapper identity are all separate dimensions. Future use should retrieve this chain when deciding where an adapter must call native lifecycle hooks or how independently allocated wrappers can share an underlying object. It should not copy the historical implementation blindly or infer current project behavior.

Relevant full contexts: endpoint objective header/implementation, score implementation, scoreboard implementation, native scoreboard implementation and identity reference, plus NonOwnerPointer. The public commits below identify each patch for direct inspection.
