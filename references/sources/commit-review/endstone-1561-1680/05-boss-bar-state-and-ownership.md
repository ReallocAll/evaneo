# Boss-bar state, audience identity, and client-ready timing {#boss-bar-state-audience-identity-and-client-ready-timing}

Scope: assigned Endstone ordinals 1561–1680, August 2024; historical static analysis, not a current-version verdict.

## API construction and revision {#api-construction-and-revision}

The boss-bar sequence starts with an abstract interface, then color/style vocabulary, stored state, native packet modeling, actual sending, generalized flags, Python bindings, and a server factory. Intermediate commits are not silently treated as complete. Grey is replaced by Pink; raw-player storage is replaced by UUID membership; a dedicated darken-sky boolean becomes a flag set. These observed revisions provide more useful evidence than a timeless summary that the final API was inevitable.

The implementation avoids redundant broadcasts when a scalar property has not changed. Visibility sends add/remove updates, and offline UUIDs are pruned when resolving players. This is concrete state synchronization. It is not a complete server-managed resource system: the server factory returns unique ownership without tracking bars globally, and the concrete class has no destructor that calls removeAll. Plugin/application lifetime therefore matters to client cleanup.

## Identity and ownership boundaries {#identity-and-ownership-boundaries}

Using UUIDs avoids retaining raw Player pointers between operations. Returned lists and Python reference policies still do not own native players after disconnect. More importantly, the packet's boss_id is the recipient's actor ID rather than an ID allocated per bar. Two bars for the same player thus share that identifier in the examined implementation. The resulting client presentation was not tested; the static identity collision limits claims about multi-bar support.

Membership methods send even if an insertion/removal did not change the set. Progress rejects ordinary out-of-range values but not NaN. Invalid flag sentinel values can reach bitset bounds checks. These are bounded implications of the implementation, not a claim that all input behavior was audited. The relevant lesson is to distinguish local C++ ownership, native player lifetime, protocol resource identity, and cleanup messages.

## Join timing {#join-timing}

1645 changes PlayerJoinEvent to run after setLocalPlayerAsInitialized, explicitly aiming for client readiness. The retained body then recalculates permissions and updates commands. This is a timing-contract change useful for UI plugins, but it does not prove that every client subsystem or packet is ready at that point. No join-phase or boss-rendering tests are added.

## Evidence and application {#evidence-and-application}

The full boss implementation/header and player join hook were read at the unit endpoint, alongside every incremental diff. Use this family for state-driven packet APIs, recipient lifetime, separate resource identity, factory ownership, and event timing. There were no runtime client checks, destructor-cleanup tests, or Python lifetime tests; mocks only mirror API signatures.
