# Lifecycle reset, plugin reload, and Python environment ownership {#lifecycle-reset-plugin-reload-and-python-environment-ownership}

Scope: assigned Endstone ordinals 1561–1680, August 2024; historical static analysis, not a current-version verdict.

## Observed design and its evolution {#observed-design-and-its-evolution}

The meaningful decision is a coordinated reset of server-owned plugin and command surfaces, implemented in stages rather than as a transaction. Data reload is introduced first, then a console command, then the server sequence that clears plugins/commands, reloads data, rebuilds plugins in two enable phases, sends a Reload event, and updates client command lists. Python loader ownership moves from runtime to core with an exact source relocation and a changed public embedding dependency. The command map is constructed only after world/thread startup, so startup plugins and post-world command availability have distinct timing.

Two alternatives are explicitly visible rather than invented: importlib.reload after importing each entry point is replaced by deleting prefixed sys.modules entries; trusting the embedded executable is repeatedly revised into a prefix-based executable search located in the loader. Installation changes from --user to a plugin-local --prefix, then cleanup and site.addsitedir move into each load. These are dated responses to concrete embedding assumptions, not a universal recommendation to wipe environments or to prefer sys.prefix in every Python application.

## What reload actually clears, and what it does not establish {#what-reload-actually-clears-and-what-it-does-not-establish}

Full plugin-manager, loader, server, and command-map contexts were read. PluginManager clears plugin registries, owned loaders, event handlers, permissions, and defaults after disabling plugins. CppPluginLoader owns plugin objects in unique_ptrs; successful dynamic module handles are not managed by a corresponding unload lifecycle in the inspected header/implementation. Python loader destruction handles its pybind object under the GIL. Those observations matter because clearing a registry is not synonymous with quiescing tasks, native references, or imported module state.

The server source explicitly leaves waiting for async tasks and dependency-graph cleanup as TODOs. The historical review recorded the six scheduler implementation/header blobs as identical to the earlier 1479/1560 endpoint.  No scheduler cancellation is added by the new clearPlugins/disable paths. Existing task/plugin references therefore remain an unresolved lifecycle dependency, not something made safe merely by firing disable callbacks. Permission subscription structures and native command containers outside the four snapshotted maps are also not shown to be reset exhaustively.

The recursive-mutex repair addresses one concrete nested-lock problem in rebuilding defaults. It is not a concurrency proof. The native command baseline is global and copies enums, enum lookup, signatures, and aliases; restoration is a partial modeled-state reset. Neither the public Python reload binding nor server.reload itself enforces the console restriction applied by the command wrapper, so invocation context must be assessed separately.

## Installation and failure boundaries {#installation-and-failure-boundaries}

At the endpoint, the loader invalidates imports, removes endstone_-prefixed modules, deletes .local, invokes pip, adds site directories, and discovers entry points. subprocess.run does not check its exit status. Deletion before installation has no rollback; imported objects held elsewhere can survive module-cache eviction. Package discovery is broader than the newly installed directory. These are failure/ownership limits in a trusted plugin loader, not a security sandbox claim. No package or plugin was executed for this review.

The shutdown API schedules a graceful native request and adds OS signal entry points. Linux's signal handler reaches nontrivial scheduler operations; signal safety is not established. It is distinct from the earlier unknown shutdown-crash cause, which remains unknown. Logging wrappers improve formatting-error containment, including severity-method delegation, but fallback logging can still fail. These mechanisms are useful lifecycle evidence only with those limits retained.

## Validation and applicability {#validation-and-applicability}

No reload transaction test, malformed-plugin fixture, failed-install test, async-quiescence test, executable-search matrix, or runtime shutdown test appears in this chain. Mock API additions are recorded per source. Use this material for staging and dependency analysis, explicit cleanup ownership, and the cost of exposing lifecycle operations through multiple entry points. Do not promote the intermediate implementation into a general safe hot-reload recipe.

### 1665 — fix: use site.addsitedir to add installed plugins to path {#commit-1665}

Source: [ebc51f989168feb0b000b08ed6e4b27d64e7e3f5](https://github.com/EndstoneMC/endstone/commit/ebc51f989168feb0b000b08ed6e4b27d64e7e3f5); committed 2024-08-27T16:37:59Z; Git author Vincent. Disposition: `substantive_revision`.

The loader now deletes its .local installation tree on each load, reinstalls wheels with pip --prefix, and uses site.addsitedir for the computed site-packages directories. Full endpoint context confirms subprocess.run does not use check=True and its result is not checked, so installation failure is not a transactional abort before entry-point discovery. Deletion precedes installation and no rollback is provided. Entry points are discovered from the environment broadly, not only a cryptographically isolated plugin set. The change improves path integration but leaves reload side effects and ownership constraints explicit.

Changed paths: `python/src/endstone/_internal/bootstrap/base.py`, `python/src/endstone/_internal/plugin_loader.py`.
