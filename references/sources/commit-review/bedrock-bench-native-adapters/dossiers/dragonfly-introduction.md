## Architectural problem {#architectural-problem}

Dragonfly is a Go library rather than a standalone packaged server with the console interface assumed by the harness. The solution is a small server application, `dfbench`, built from the pinned library plus benchmark-specific observation/control surfaces:

- `main.go`: CLI flags, server startup, version/build facts, ready/spawn signals, lifetime, idle loader;
- `config.go`: Dragonfly's normal user config plus the explicit `[Bench]` API-only settings;
- `console.go`: stdin command parsing and world/player-owned command tasks;
- Python `DragonflyAdapter`: provenance-aware build/install, configuration rendering, launch, reply parsing, facts, and capability declarations;
- paired Go/Python tests and a shared rendered-config fixture.

The source intends to preserve Dragonfly's example-server behavior when no Bench settings are supplied. This is an intent whose concrete implementations can be inspected: missing config is generated from `server.DefaultConfig`, omitted world settings remain unset, and the wrapper then uses Dragonfly's `UserConfig.Config`/server constructors. It does not prove that every future Dragonfly default or example behavior is reproduced. The wrapper's own console, startup facts, and process lifetime are part of measured cost.

The adapter directly implements `ServerAdapter`, rather than borrowing BDS's world and command assumptions. It advertises Windows, Linux, and Docker; the target is the host architecture, with Linux selected for Docker. macOS-native execution is rejected. Registry discovery makes the new concrete module available without a central switch. Protocol 2193 is checked against the built helper, rather than presumed from a friendly version label.

The official build path establishes multiple checks:

1. Read the helper's go.mod/go.sum without invoking Go. Require its Dragonfly version to equal the artifact pin, reject any go.mod `replace` directive, and require the expected checksum entry.
2. Resolve the Go executable and ask `go env GOVERSION` under the selected build environment. This resolved toolchain version enters the cache key.
3. Run `go mod download -json <module>@<version>`. Require returned `Sum` to equal the manifest `h1`; require a real downloaded zip; independently check its byte SHA-256 and size against the pin.
4. Build with `CGO_ENABLED=0`, selected GOOS/GOARCH, `GOWORK=off`, readonly module mode, baseline `GOAMD64=v1` on amd64, trimpath, disabled VCS stamping, stripped debug/symbol information, and empty build ID. The helper embeds harness version and the first 12 characters of normalized helper source hash.
5. Run `-version` and require the claimed Dragonfly tag and protocol. Run `-defaults`, require parseable TOML, and store both outputs beside the executable.
6. Record binary SHA-256/size plus module artifact identity. Use the shared staged, read-only cached-install mechanism and fresh writable copies per run; reject a copied executable hash mismatch.

The source digest covers sorted top-level non-test Go files plus go.mod/go.sum, normalizing CRLF to LF. It intentionally excludes tests, docs, and settings templates. The cache key adds server version, target, toolchain version, and harness version. This is coherent for the source layout at this commit. Future embedded files, subpackages, or compile-time inputs outside that selection would need corresponding hash coverage; such content is not shown in the submitted source.

### What reproducible means here {#what-reproducible-means-here}

The documentation claims that identical source/toolchain produce identical binary bytes. The flags remove several common nondeterministic inputs, and tests assert that they are passed. This review did not compare independent binary builds. Shared `bots.build_env` starts from the ambient environment and overwrites selected variables; it does not hermetically erase every Go experiment, architecture feature, proxy/checksum setting, or global Go configuration. Consequently the cache key and flags are strong reproducibility inputs, not a universal proof of complete environmental identity. The main module receives an additional byte-level zip pin; the other dependencies rely on Go's dependency/checksum machinery and the checked-in sums.

For a cross-target build, the target executable cannot run on the host. The helper builds a second executable for the host and uses that sibling's `-version`/`-defaults` output, then labels the recorded build metadata with the requested target. This verifies same-source host behavior and records the target artifact's hash; it is not a run of the actual cross-target artifact. Platform-sensitive defaults or startup behavior remain a runtime validation concern.

A user-supplied prebuilt artifact is adopted into the cache and hashed, then self-describes through `-version`/`-defaults`. It must run on this host and match the requested version/protocol. A linked replacement or workspace module reports `devel`, deliberately separating a fork from the official pin. This catches ordinary mislabeling and preserves provenance but does not authenticate a malicious binary's self-report or establish source equivalence. It is marked local/unpublished. No prebuilt artifact, build command, binary, or upstream test was executed during this research.

## Configuration: compare against the actual build, then write only owned keys {#configuration-compare-against-the-actual-build-then-write-only-owned-keys}

`config.go` builds a configuration from Dragonfly defaults and a Bench extension. A missing file creates only Dragonfly's default user config. Existing input rejects unknown top-level tables and unknown Bench keys; unknown keys nested in Dragonfly's own tables are delegated to that library, which the comment says ignores them. The special benchmark *settings specification* at `servers/dragonfly/config.toml` is intentionally not a runtime config; a Go test ensures its `schema`, `file`, and category tables fail instead of quietly becoming ignored settings.

Bench defaults mirror the example server: debug logging, idle ticking off, autosave ten minutes, and nil tick-range/difficulty/game-mode pointers so an existing world keeps its stored values. For `-defaults`, world values are filled from a fresh LevelDB provider's default level data. The distinction matters: “default for a new benchmark world” is not the same as “overwrite an existing world's settings.” A positive save interval is seconds, zero restores the ten-minute default, and negative disables it.

The Python settings plan requires schema 1, the intended config filename, recognized override categories, dotted keys, unique category ownership, and a nonempty reason. Every desired key must exist as a scalar/list in the build's saved defaults. Placeholder rendering takes scenario and machine values; booleans, integers, strings, and lists are coerced according to the default's type. A typed value equal to its default is still written and later checked, but omitted from the list of overrides.

The plan explicitly sets loopback listening, offline login, server name, info logging, and idle ticking as harness settings. Parity settings include max players 200, view radius 10, tick range 4, easy difficulty, survival mode, persisted player/world data, a fixed world directory, and 300-second autosave for the original 6000-tick workload. `autosave_ticks / 20`, rounded to seconds, is a nominal conversion; it is not proof that each server's wall-time and tick-based save schedules are equivalent when overloaded.

The shared `testdata/config.toml` is a useful cross-language boundary. Python asserts byte identity between its rendered spread config and this fixture; Go parses the same bytes and checks the expected user/Bench values. Unlisted settings remain absent and keep the build's defaults. This is stronger than independently authoring two plausibly similar fixtures.

After a run, Python rereads only the keys it wrote and reports missing/changed values. Additional unowned keys do not themselves fail. This differs from LeviLamina's all-leaf snapshot readback at the same historical point. Neither form proves a runtime's effective internal values. dfbench additionally writes observed difficulty/default game mode and runtime CPU information, but `tick_range` in that facts file is the configured pointer, and `save_interval_s`, `idle_ticking`, and log level are configuration-derived values, not independent probes of every subsystem.

There is a concrete disabled-autosave facts edge case: `saveInterval()` returns a negative `time.Duration(-1)` sentinel, but `writeFacts` converts `bench.saveInterval().Seconds()` to an integer. A negative nanosecond becomes zero after that conversion, so `save_interval_s` does not faithfully preserve the off sentinel. The initial benchmark config uses 300 seconds, so this is a static supported-path limitation rather than an observed failure of that initial run. Tests check the negative duration and positive facts independently, without a disabled-facts assertion.

`facts()` tolerates absent or malformed JSON by using an empty mapping and fallback configuration/build information. This allows the run record to retain partial metadata, but means null/fallback facts must not be described as successful runtime observation. A parsed JSON value of an unexpected non-object type is not explicitly rejected before `.get` calls in the submitted adapter; that robustness boundary is not covered by the inspected fake-facts test.

## Startup, process identity, and shutdown {#startup-process-identity-and-shutdown}

`serve` reads configuration, routes slog/standard logs to stdout with microsecond timestamps, subscribes normal chat output, constructs Dragonfly, applies selected settings to all three worlds, optionally installs an overworld idle viewer, and registers program-end closure. It logs a version banner and Bench description, then writes `dfbench.json`. Only after `srv.Listen()` returns does it emit the harness-specific `Server started.` line and launch the stdin console goroutine.

Dragonfly's own earlier `Dragonfly server started.` log is deliberately insufficient readiness. Player readiness is also precise: the accept loop runs in the transaction that added the player to its world, and only then adds the handle to the roster, installs a quit handler, and prints `Player spawned:`. Network connection or chat join output is not accepted as proof that a command can target the player.

Console EOF stops the server, so a vanished harness does not intentionally leave a detached daemon. `sync.Once` makes repeated console stop idempotent. `Scanner` errors are not separately inspected; an input read/token-limit failure follows the same close path and logs “Console input closed.” This is a static diagnostic limitation, not a reproduced failure.

A failure to write startup facts returns after constructing the server and registering program-end handling but without an explicit local `defer srv.Close()` in the wrapper. Whether program exit fully performs cleanup is an upstream/lifecycle concern not exercised by the shown tests. The in-memory console test's teardown does explicitly call stop.

The measured process is dfbench itself. Go goroutines can migrate among operating-system threads; `tick_thread_rule = "none"` intentionally makes tick-thread metrics inapplicable. The appropriate CPU cost scope is process CPU, not the CPU of a guessed thread or BDS-style CPU/tick. Startup facts record Go's GOMAXPROCS and CPU count; launch removes ambient GOMAXPROCS, GOGC, GOMEMLIMIT, and GODEBUG. Documentation says the harness pins the suspended process before startup; this introduction's adapter only returns the launch specification and does not by itself prove that platform machinery worked on a real machine.

No native crash files are declared. Go panic text and goroutine stacks are preserved through console-tail collection in the wider harness. The added crash fixture is synthetic and unprefixed; parser tests preserve it as such rather than claiming it carries a normal log level.

## Counter semantics and the idle-observer intervention {#counter-semantics-and-the-idle-observer-intervention}

`gametime` submits a task to the overworld and replies with `tx.CurrentTick()`, not the daylight-controlled world time. This chooses an executed-tick counter suitable for receive-time throughput calculations. The submitted explanation says Dragonfly skips ticks in worlds without viewers, so an empty world leaves the counter at its initial value; a naïve monotonicity gate would confuse idle optimization with a stalled server.

`Bench.IdleTicking` changes that baseline explicitly. `keepTicking` creates a radius-zero loader with a no-op viewer, moves it to (-100000, 0, -100000), and never asks it to load chunks. The intent is to provide a viewer for tick progression without bringing benchmark terrain into tick range. The setting is recorded as a harness override rather than silently hiding this intervention.

The Go test constructs two real in-memory library worlds, waits 600 ms, then asserts that the empty world's counter is at most one while the kept world's counter advances to at least three. It is skipped under short testing. That specified test is stronger than a synthetic tick-string parser for the counter premise, but it was not run here. It does not count chunks, loader work, CPU overhead, or tick contents. The documentation's “loads nothing”/“changes nothing but that” claim is therefore broader than the shown assertions. During a populated overworld the bots already provide viewers; after they leave for other dimensions the loader again changes whether overworld ticks continue.

This mechanism makes a metric observable by changing idle behavior. Treat idle CPU under IdleTicking as the cost of the configured harness run, not unmodified Dragonfly idle cost. Executed tick throughput still does not establish equal work per tick or wall-clock MSPT across implementations.

## Ownership-aware commands and their completion boundaries {#ownership-aware-commands-and-their-completion-boundaries}

The console reader parses one command per line, with optional slash, case-insensitive command name, and double quotes for names containing spaces. It validates arity and reports errors at error level so smoke logic can observe rejected commands. Numeric coordinates reject NaN/infinity; dimensions, modes, effects, and fill blocks are whitelisted. `fillnear` uses integer offsets, normalizes corners, rejects ordinary volumes over 32,768 blocks, clips out-of-range Y positions, and counts blocks actually set. Arithmetic is machine-int arithmetic without a separate overflow guard for extreme user-supplied offsets; the normal generated benchmark offsets are bounded elsewhere. This is a helper-input boundary, not evidence of exploitation.

Commands mutate world-owned state inside `World.Do` or `player.Do` tasks. The stdin loop can continue reading while slow worlds delay execution/replies. A fan-out helper submits a task to each of overworld/Nether/End, uses a WaitGroup, and runs the aggregate callback after completion. Player enumeration collects targets before mutating them so operations that remove/move a player do not invalidate the iteration. A mutex-protected roster provides case-insensitive name lookup rather than using the library lookup the comment identifies as unlocked. Its remove operation compares handle identity, so an old session's delayed quit cannot delete a newer same-name session. The roster unit test specifies this concrete lifecycle invariant.

Positions are collected under each world transaction, protected by a result mutex, sorted by name, and emitted as a declared count plus one line per player. Python returns `None` while the response is absent, malformed, or incomplete and returns an empty list only for an explicit zero count. It permits unrelated lines interleaved with the reply. This preserves “unknown” versus “no players.” It does not provide a globally simultaneous snapshot across worlds, validate finite float values on the Python side, or correlate concurrent position requests with request IDs.

Cross-dimension teleport removes the entity in its source transaction and queues insertion/teleport on the destination world. The completion callback logs success after the source-side callback returns, before the queued destination work is explicitly awaited. `inEachWorld` also discards task errors in its completion callback. These are meaningful static boundaries: command submission, source-side mutation, destination completion, and success reporting are not universally the same event. The in-memory happy-path test checks a subsequent position after teleport but does not prove slow/failed destination ordering or error propagation.

Supported controls cover teleport/dimension teleport, effects/clear, kill, kick, game mode, list, weather, relative fill/setblock, help, and stop. Kill uses void damage and distinguishes already-dead from invulnerable players. Effects translate a vanilla amplifier to level+1 capped at 255, support finite/infinite durations, and optional hidden particles. Unsupported chaos actions have explicit reasons: no mobs/loot cleanup, no dynamic random-tick game rule, no locator bar, and no ticking-area commands. Capability declarations avoid silently treating an unsent action as successful work. They still do not establish that supported commands are semantically identical to every vanilla command.

## Fairness and feature evidence {#fairness-and-feature-evidence}

The introduced feature table is version-specific and marks implemented nonvanilla mechanics as partial unless claimed compatible. The source explicitly records flat-only worlds, no normal terrain/structures, no client-side generation, no mobs/AI or entity collision push, no authoritative player movement/physics, and no locator bar. Item entities, hunger/damage, redstone, random ticks, fluids, falling blocks, lighting, and dimensions are independent/partial implementations. Subchunk requests, matched autosave interval, and encryption are declared vanilla, with encryption not exercised in offline runs.

Most rows link to exact files/lines in the pinned Dragonfly revision; some use intended observed counters. This review read those declarations, the helper, and the adapter, not the whole upstream Dragonfly implementation behind every linked feature claim. Presence of a source URL or counter name is provenance, not proof of complete behavioral equivalence. The feature test checks that exercised keys are declared and have evidence or an observed counter; it does not execute those features.

The documentation warns that client positions are accepted, so bots teleported to Y=300 hover; flat generation is much cheaper than vanilla terrain; worlds saved by other engines may fail to load or fall back to flat. Consequently the adapter marks its worlds `generator="flat"`, and any template must be generated for Dragonfly rather than treated as a universally portable pre-generated workload. The source's reports about other-server world imports are contemporary benchmark context, not reopened analysis of decade-old Nukkit source history.

Fidelity V1 here means the implementation is not deliberately skipping its own implemented work for speed; it emphatically does not mean Minecraft feature completeness. Process CPU, TPS, chunks delivered, and load time must carry missing-work/context disclosures. A faster or cheaper Dragonfly run cannot establish superior performance for an equivalent vanilla simulation.
