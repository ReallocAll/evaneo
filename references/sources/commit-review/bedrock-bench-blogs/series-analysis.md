## Reading map and shared experimental frame {#reading-map-and-shared-experimental-frame}

The index organizes measuring, finding bottlenecks, fixes, network work, and unshipped ideas. ## Measurement and diagnosis {#measurement-and-diagnosis}

### profile-vanilla.md — Validate the load before pricing capacity {#profile-vanilla-md-validate-the-load-before-pricing-capacity}

Bots claimed to walk, yet repeated console position queries showed no change and movement corrections stayed zero. They omitted the client loading-screen-closed message; the server held them in place and ignored movement. Earlier-than-October-10 capacity runs therefore described frozen players and were optimistic. The fix sends the message after spawn. Protective effects and y=300 teleport keep bots safe on ungenerated terrain; fake flat-ground walking produces correction work a genuine client would not, so correction rate belongs next to movement metrics.

At 60 spread bots, 640-block separation and requested radius 16, joins occurred within 18 seconds but main-thread saturation continued beyond ten minutes. Low incoming chunk rate did not prove settling: a saturated producer can deliver slowly while work remains. Unique chunks per player and a stable TPS trajectory gave a roughly 17-minute settle; 120 players took over half an hour. After autosave improvement the walking workload itself grew: roughly 100,000 versus 71,000 unique chunks. Compare absolute work and workload, not percentages alone.

Without Windows administrator rights, the Visual Studio collector sampled at 4 kHz. Startup stacks lagged 5–10 seconds, so the first 12 seconds were excluded. Whole-system decoded traces grew about 17 MB/s, 2–5 GB per trace; writing them triggered Defender on 2–3 cores. Streaming decoder output directly into parsing avoided that perturbation. A 75-second trace decoded in about 50 seconds. Vanilla TPS was inferred from gametime delta over wall time, queried every five seconds. Main-thread sample gaps over 0.75 ms provided another idle/tick signal, not a universal clock. Profiling cost about 6% TPS at saturation, hence separate unprofiled headline and profiled diagnostic windows. Concurrent servers/harnesses polluted runs; record machine load. Even the improved 60-player workload required 803 seconds for views, with a delivery burst temporarily lowering TPS to about 18.

### player-cost.md — Model shape, then calibrate price {#player-cost-md-model-shape-then-calibrate-price}

Loop audits count entity-property lookups, allocations and container comparisons rather than judging function length. A locator-pair lookup recomputed hashes during ordered-table comparisons, about 2 log2 n computations, with 9,900 pairs at 100 players. Standalone C++ skeleton replicas omit gameplay and keep warm data, so they estimate a floor rather than real server latency. Corrected pair-check price is 240–280 ns, 2.4–2.8 ms per tick; combined replicas suggest 5–8 ms versus roughly 11 ms profiled. A 2.2-versus-4.7 ns repeated result warns against false precision.

Three audit failures explain the need to trace actual control flow: a client-only branch was priced for a dedicated server; a lean player-dot routine delegated to generic code that copied heap strings; a huge player function mostly handled conditional respawn, not ordinary ticks. A locator model with N² log N, N³ and N² terms fitted at 100 predicted 3.25 ms at 60 against 3.18 measured. Its 200-player roughly 60 ms is extrapolation, not an observed run. The early 120-player 19 ms locator observation includes joins and is not a clean steady comparison.

Four prototypes atop autosave on 1.26.51 started at 10.75 TPS / 93 ms. Blending cache saved about 11 ms, player scans 5.6, locator 7, publisher about 11; together about 19–19.7 TPS / 50 ms with random ticks still 22 ms. The shipped implementations and later 1.26.52 total are separate states. Revisions make that distinction more explicit.

### codegen.md — Respect binary and allocator boundaries {#codegen-md-respect-binary-and-allocator-boundaries}

Windows BDS was an optimized link-time-optimized release without PGO, rather than an accidentally debug-like build. CFG cost about 2% and was accepted as a security tax. Allocation cost approximately 2% steady and 8% joining before autosave removal. The Linux mimalloc A/B was on an already-improved Endstone development build, not the 11-TPS Windows vanilla baseline: at 50 players 47.0 to 36.6 ms, at 60 default allocator 17.1 TPS versus 20, with 13–15% extra memory. Each configuration ran once. Windows allocator replacement cannot safely intercept only server allocations when CRT ownership crosses module boundaries; free with the wrong allocator corrupts heaps. Redirect the runtime consistently or classify foreign pointers. Only Linux shipped the allocator change.

A new zlib instance per outgoing batch allocated hundreds of KiB and Windows returned large freed blocks to the OS, creating refault work. Existing development-branch libdeflate work was backported. On 39.7 MB / 3,465 real gameplay batches, throughput was 25.5 versus 117.9 MiB/s, 4.6× faster with 0.40% larger output; a higher setting traded down to 1.6× speed for roughly 1% smaller output. A synthetic corpus showed only 1.85×. Cross-decoding against real zlib was reported when the change first landed, not claimed as a newly rerun continuous test. Post-autosave CFG became 3.7% without meaningful absolute growth; allocation 4% steady / 15% joining. Absolute ms prevent denominator mistakes.

### linux-fill.md — Instrumentation must prove it is active {#linux-fill-md-instrumentation-must-prove-it-is-active}

Linux launch required executable permissions after Python ZIP extraction; timestamp parsing and process detection needed vanilla-specific paths. Packaging silently overrode an instrumentation option, so a successful build was insufficient: inspect the built library for the flag's effect. Stale test plugins, Windows path limits and a bash queue that advanced after a stopped child all contaminated workflow. A between-jobs file gate replaced the ineffective pause.

Chaos analysis initially partitioned by commands sent. Two of 31 Linux tick-speed changes never executed due to Endstone's full console input queue, and Windows delays reached 2.5 minutes. Partition by server-confirmed rule changes. This input-loss bug remained in 0.11.14. A concurrent Windows chaos run depressed Linux normal-speed TPS to 17.2; unchanged-build rerun gave 19.3. Normal tick speeds were 0, 1 and 3, distinct from stress changes as high as 1000.

Reported Linux rows: vanilla / 0.11.13 / 0.11.14 steady TPS 9.46 / 9.45 / 20; main-thread ms 105.7 / 105.9 / 46.5; view median 194 / 192 / 130 seconds; chaos normal-speed TPS 14.8 / 10.2 / 19.3; RSS GB 3.96 / 4.06 / 4.54. Chaos uses a development build predating final compression/generation changes. Join storms still reached a lowest 15-second TPS average of 8.0 on Linux versus 17.5 Windows; steady success does not remove burst weakness. Locator differences are discussed below, not hidden in a zero-differences headline.

### custom-bench.md — The denominator is simulated work {#custom-bench-md-the-denominator-is-simulated-work}

PocketMine-MP 5.44.3, Nukkit b3caad6, PowerNukkitX 3.0.5 and Dragonfly 1793369 required protocol/login adaptation, per-bot numeric fake XUIDs, flight handling, and raised per-IP limits for 100 localhost clients. PocketMine's 200-datagram/10-ms limiter banned all bots for 300 seconds; its default 1 GB main-thread cap then crashed at 23 seconds and was disabled for a rerun. Record those interventions, not a misleading default-only success. Nukkit/PNX auto-tick-rate was disabled because gametime could jump over skipped simulation and overstate TPS.

The article's fresh-world table reports Endstone 20 TPS / 1.04 cores / 4.7 GiB; Dragonfly 20 / 0.56 / 1.9; PocketMine 4.6 / 1.07 / 6.0; PNX 1.3 / 3.67 / 15.8; Nukkit shutdown. Lowest loading TPS is 16.5, 14.6, 1.5, 0.7 respectively, with Endstone's same-session lowest instead 18.6. These are heterogeneous runs and configurations, not rankings of equivalent simulation. Nukkit had 63 spawn timeouts and a main-thread autosave of about 17,600 chunks that triggered watchdog shutdown. PNX's chunk rate fell below settle threshold while median view was only 16 chunks: stalled is not settled.

Pregeneration changed results: Nukkit generated 53,802 chunks in 460 seconds and achieved steady 20 TPS, but about 5.7 while loading. PNX ignored generator requests without nearby players, so bots toured the grid; subsequent 4.3 TPS was dominated by synchronous disk reads/zlib in eight of ten stack samples, not its roughly 3% GC. World interchange attempts regenerated, fell back to flat or crashed. All four custom servers left bots hovering without movement corrections and lacked locator bars. Dragonfly's world was flat with no mobs. None supported client-side terrain generation, so filled views carried 453–480 chunks versus Endstone's about 103. Attribution of speed must preserve these differences and protocol adaptations.

## Main-thread architecture and behaviour preservation {#main-thread-architecture-and-behaviour-preservation}

### tick-threading.md — Parallelism is an ownership audit {#tick-threading-md-parallelism-is-an-ownership-audit}

The tick loop catches up at most roughly two ticks and drops excess elapsed debt; 10 TPS does not later recover all lost simulation. Old MSPT timed only level tick, excluding network/outer-pass work, and rounded to integers; 0.11.14 times the whole pass with finer precision. ECS systems are ordered on the main thread. Chunk work has both ordinary-system and ticking-area entry routes. Chunk order is reshuffled every 20 ticks, but existing ordering variation does not itself prove arbitrary concurrent execution safe.

Four ownership signs constrain parallelism: block-entity try-lock failure loses that tick (more failures would change gameplay); loaded-chunk table reads require no simultaneous insertion/removal and mutations stay on the main thread; block-access objects contain mutable thread-affine caches; some object kinds defer destruction to the main thread through a locked release list. The correction narrows “all objects” to “some kinds,” and clarifies read-versus-write safety. Separate block-access objects and main-thread publication are prerequisites, not a finished parallel-tick design. The release instead reduced main-thread work, woke existing terrain workers and optimized one network worker; process CPU roughly 1.07 to 1.04 cores while tick throughput more than doubled.

### actor-tick.md — Follow activation producers before every consumer {#actor-tick-md-follow-activation-producers-before-every-consumer}

A truncated analysis-tool output initially hid the ECS half of the main tick and falsely suggested mobs ran elsewhere. Read to the real end; silent output truncation is not negative evidence. Rather than examining hundreds of systems, trace who sets the per-tick simulation flag: ticking chunks, rider/vehicle handling and special entities. The report finds no distance activation range within ticking chunks. Simulation distance/ticking areas determine normal activation, with exceptions. An idle cow still runs goal selection, tempt and despawn/player queries. At the studied load goal selection was 5.9%, player traversal/bookkeeping 7.8%.

Distance-throttled mobs and alternating-tick goal selection were rejected because breeding, movement, farm throughput or reaction delay changes. Spigot/Paper and Java provide comparisons, not permission to change Bedrock. A cache that returns the same ordered players was accepted instead.

### block-sim.md — Find ownership of a hot helper {#block-sim-md-find-ownership-of-a-hot-helper}

Simulation distance four was inferred from actual loop bounds as a rounded 57 chunks, not an assumed 9×9 = 81 square. Every loaded chunk registers with redstone even in natural terrain; registration costs roughly 0.75 ms and steady redstone checks covered the loaded area, not merely active circuitry. Block-entity membership was also broader than “has work.” Per-block guards and lock-style operations deserve multiplicity analysis, but removing a guard still requires ownership proof.

The apparently simulation-related random-loaded-chunk helper was owned by incremental autosave, not random block ticks. It consumed roughly 45% main-thread time, with up to 20 linked-list walks per tick. After its fix, 60-player work fell to 47–49 ms; random ticks were 16.4 ms and redstone 7.0. Reprofile after removing a dominant cost rather than preserving old rankings.

### chunk-storage.md — Amortize selection without losing the random sequence {#chunk-storage-md-amortize-selection-without-losing-the-random-sequence}

Generation submission used a nonblocking try-lock; save wrote changed pieces rather than whole chunks, rejecting two plausible initial theories. The actual hot path draws an index then linearly walks a linked loaded-chunk table, up to 20 times until one dirty chunk is saved. A flat position snapshot makes selection constant time and rebuilds each 400 picks. At the heaviest stated load rebuilding costs about 16 ms; at maximum pick rate it occurs about once a second, under 1 ms amortized per tick, while retaining a possible individual spike.

Consume random numbers exactly as vanilla to preserve downstream shared RNG state. Snapshot staleness changes which chunk is saved next; authors classify this as save timing, not exact selection identity. A vanilla-1.26.51 same-seed 60-bot prototype raised joining TPS 12.7 to 19.9, lowered main-thread CPU 870 to 459 ms/s, and then held 20 against 9.6–13.7 through sampled post-join time up to 350 seconds despite more loaded chunks. Shipped Windows 6f0c32205 / Linux bec9a2fd7. Broader release results are not isolated autosave attribution.

### ai-nav-collision.md — Audit gates and shared work {#ai-nav-collision-md-audit-gates-and-shared-work}

Pathfinding has a bounded search; solid-entity collision is gated by a nearby-solid flag, but pushing queries run even for isolated mobs. Most idle goals are unthrottled, a few have cooldowns, and target scans stagger across mobs. Repeated neighbour retrieval/sorting for flee goals and per-path-node allocation remain candidates. Twenty-two nearby-player uses are a subset of dozens of global player-list consumers, not all the same nearest-player semantic operation. Despawn may ask whether any player is near, not require the nearest one.

Mob count barely increased across the studied 60/100 runs; player-driven calls explain the growth. The player walk increased about 6.4 ms, one contributor rather than the whole cause of the doubled tick time. The 5.6-ms prototype included two smaller optimizations omitted from release. Large farms/entity-dense workloads were not tested; do not infer their safety/performance from natural spawns.

### hotpath-overheads.md — Zero workload masks multiplicative terms {#hotpath-overheads-md-zero-workload-masks-multiplicative-terms}

Area-entity queries gather chunk entities then append players by global traversal. Nether entities still inspect Overworld entries to filter dimensions. Entity-update relevance does similar work. A flat mob-free benchmark makes mobs×players terms zero while player×player terms remain. In the real natural-world runs mobs did not scale with players; extrapolating quadratic mob costs requires that additional workload assumption.

Corrections separate pet owner-by-ID scans from shared nearby-player traversal, call 2,500 walks “full-walk equivalents” inferred from timing, and identify input catch-up, touches, updates, spawners and minecarts as sources of extra visits. At low TPS input work per tick inflates because clients send by wall clock. The cache checks that players are still in-game, not inaccurately “alive.” This article and player scans describe the same implementation and benchmark, not two replications.

### light-spawn.md — Count shipped data and validate the expensive term {#light-spawn-md-count-shipped-data-and-validate-the-expensive-term}

Lighting queues only meaningful opacity/emission changes, batches by section, budgets main-thread relight, and lights new terrain on workers; steady profile was 0–0.2%, so it was left alone. A Starlight-like larger-region pass might alter boundary-dependent outcomes. Natural spawn chances are rare but attempts repeatedly count mobs and scan columns. Every ticking chunk consumes a shared RNG draw even without a spawn; skipping it would perturb later events. A 1-ms estimate at 100 was already low relative to the 60-player observed roughly 1 ms.

Behaviour-pack data was not strict JSON. Of 76 despawn definitions, 73 used the built-in rule and only three filters, overturning focus on expensive nearest-distance filters. A 1,000–3,000 mob assumption predicted 5–15 ms despawn work; measured nearby-player cost was about 0.7 ms. Full-walk equivalents were about 250, flat from 60 to 100, not the estimated 1,250–3,750. Per-visit price roughly 29 ns was sound; multiplicity was wrong. Keep both parts of the model independently falsifiable.

### opt-player-scans.md — Preserve iteration semantics and lifetime checks {#opt-player-scans-md-preserve-iteration-semantics-and-lifetime-checks}

At 60 players the traversal cost 3.85 ms; at 100, 10.28. One touch scan per player per tick gives a known 10,000-visit ruler at 100 and about 21 ns per visit. Other timings imply roughly 1,570 to 2,490 full-list equivalents and 94,000 to 249,000 visits, not directly counted invocations. A Python profile cache keyed by object identity reused freed identities and contaminated later columns; invalid comparisons were discarded. Movement catch-up 0.66 to 5.69 ms/tick looked ninefold, but player-only work grew 1.4–1.7× per second, near the 1.67× population ratio. Only the traversal part added superlinear work.

A resolved-player snapshot is compared against the live list and rebuilt on change (estimated checking overhead 0.1 ms/tick across callers). Preserve order, early exit, per-call validity/dimension checks and vanilla fallback when unsafe. Entity packets compute the entity ID once and test each recipient's tracking set; about 99% reject. Hash equivalence was tested on 31,017 IDs on both OSes. Active-player count reuses the snapshot. Prototype saved 5.6 ms versus 5.5 modeled but included movement-recipient and ID lookup changes excluded from release. Reported shadow checks: Linux 47.8m walks / 3.6m packets / 1.7m counts, Windows 25.1m / 2.19m / 0.95m, zero differences. Shipped fa7b3d4eb; finite checks are evidence, not universal proof.

### opt-locator.md — Prove a no-op and retain the original slow path {#opt-locator-md-prove-a-no-op-and-retain-the-original-slow-path}

N(N−1) gives 9,900 ordered pairs at 100. Cost 3.2 to 10.9 ms from 60 to 100 grew faster than pairs alone. Ordered record lookups introduce N² log N; dot updates N²; repeatedly scanning players' existing dots N³. At 200 the model predicts about 60 ms, including 27 ms cubic. Lookup of a missing pair inserts an empty record, invalidating the assumed small table. A texture string exceeds small-string storage, so redundant copies allocate on every pair.

The fix proves when a pair cannot send anything, skips only then, otherwise invokes vanilla decisions with a private per-pair record and vanilla distance arithmetic. The cubic step collects current dots once and compares to the player list (~200 steps/player) instead of scanning each existing set repeatedly (~million steps/tick at 100). Audited intermediate lookups are read-only. Random dot IDs are still drawn in original order; equivalence allows vanilla's own ID-induced order variation. Sharing per-player state across all viewers was rejected because the player can change between viewer updates, making a cached answer up to one tick stale.

Windows shadow run: 78m pairs, zero differences. Linux: 101m pairs, 98.5% no-send proof, about a quarter differ. At 23 players, expected 506 records but vanilla had 504; existing records matched. Linux identifies pairs only by a weak hash, colliding for reported 46–66% of 100-player pairs. State overwrite causes about 23,000 extra position updates/s or a missing initial dot. Endstone retains true pairs and behaves like Windows. Thus Linux is an explicit semantic bug-fix exception to literal vanilla matching. A/B saving about 7 ms; shipped 874c1fa31. Aggregate 745m Windows and 833m Linux checks come from separate release chaos runs and must not be added blindly to earlier checks; Linux differences remain disclosed. Detailed logging supports the diagnosis, not a claim that every mismatch was individually inspected in full.

### opt-random-ticks.md — Predict reads while leaving semantics in place {#opt-random-ticks-md-predict-reads-while-leaving-semantics-in-place}

About 5,700 chunks × ~25 picks gives ~140,000 picks/tick. In one profile chunk tick cost 32.5 ms, random ticks about 22, useful block actions only 0.73. Inlining hid detail; instruction-address sample partitioning split one function into roughly 30 logical regions. First identical block check cost five times later checks, implicating cold dependent reads. Around 140 ns/pick was dominated by chunk→section→storage→block misses. The initial precise explanation of a seed write serializing all outstanding reads was later softened to an expensive stalling instruction; preserve that correction.

Replacing the loop and skipping inert sections was rejected: determining whether a palette contains tickable blocks itself costs misses, lava/water/lit-redstone semantics are nonobvious, and internal binary patch upkeep is high. Shipped warmup copies seed, predicts each platform's own positions, prefetches dependency stages for up to 256 picks/chunk, then leaves vanilla loop and RNG untouched. Wrong prefetch should harm performance only within the stated read-only design. Windows/Linux arithmetic differs for about half the seeds, so a universal predictor is wrong.

Estimated isolated saving 8–12 ms was never cleanly A/B tested. Stall patch 036a4adc8 preceded warmup 6e7417c00 and was reverted f1f0b65f1. A later comparison within ~15 ms/s (<1 ms/tick) also changed four network items, so it does not isolate the reverted patch. Do not promote estimates or confounded comparisons to measured isolated wins.

## Chunk delivery and generation {#chunk-delivery-and-generation}

### chunk-send.md — Trace, then let the profile overturn the ranking {#chunk-send-md-trace-then-let-the-profile-overturn-the-ranking}

Each player's queued view is copied/sorted by distance every tick, and readiness is tested even for incomplete chunks. A small global budget divided among players bottoms out at one chunk/player/tick at higher populations. Initial attention went to serialization/cache opportunities and sorting, but a 100-player profile gave 11.5 ms total, only 1.3 sorting, 4.2 attempts dominated by unready entries and 1.9 blob bookkeeping per attempt. Generation-priority refresh is inside that cost, 0.24 ms settled but 4 ms within a 28-ms stalled-join publisher profile.

Default chunk packets handle biomes; terrain uses subchunk requests and blob hashes. The shared blob store deduplicates in-flight storage, not necessarily serialization work. Original claims that lighting workers serialize exactly the same network bytes and discard them were corrected to more cautious duplicated subchunk preparation work. A shared-byte cache remains unbuilt and unproven. Parking and batched priority refresh dropped the prototype send loop 11.5 to 0.35 ms. Release view-load improvement includes all changes. Same-distance ordering is permitted to vary; refreshed priorities can be one tick old for client-side-generation work started during a player pass. Those are explicit boundaries, not exact execution-order identity.

### opt-publisher.md — Reduce inputs to a stable original loop {#opt-publisher-md-reduce-inputs-to-a-stable-original-loop}

Over 90% of the publisher's own sampled time landed on one readiness memory read: avoid touching cold unready objects, not merely optimize comparison instructions. A contaminated stack-cache comparison was repaired before decisions. Replacing a deeply embedded update would create maintenance debt, so a pre-pass parks out-of-view/unready chunks and lets the unchanged vanilla loop sort/send the rest. Loaded notification and view-bound changes reactivate entries; a 100-tick sweep is a backstop. The report says every readiness transition was audited; otherwise missed notifications would delay delivery until the sweep.

Refresh generation priorities once after player updates (per dimension) instead of every player, reducing lock contention and full-list rebuilds. Platform-specific chunk-position hashes must match the original in-place queue. First 256 encountered lookups are checked; mismatch warns and falls back to vanilla. A fake-player/chunk test program drove logic before live use. Parking plus refresh saved ~11 ms; shipped 099d6f028. Windows 424.7m and Linux 679.9m parked-entry checks found none vanilla would send. Linux send order differed in 149,125/371,264 checks, entirely equal-distance ties. A nearest-first contract can hold while unstable-sort tie order changes. These counters overlap broader verification aggregates.

### opt-chunk-load.md — Rates at two pipeline stages are not equal {#opt-chunk-load-md-rates-at-two-pipeline-stages-are-not-equal}

One recording reported 3.8%, 0.9% or 0.2% load setup depending on which profile was parsed first; Python identity reuse in a stack cache was responsible. Process isolation per profile prevented cross-contamination. Runs of sampled stacks separated by ~1.2 sample periods showed peaks at k and 2k, estimating ~0.75 ms per loaded chunk. A natural chunk's 35,000–45,000 non-air blocks × ~20 ns supports the magnitude. Palette-level skipping must account for all load effects, including orphaned tall plants, not only redstone. The corrected text calls this a design, not a built successful prototype.

Bot receipt ~100 chunks/s did not imply server loads at 100/s; delivery drained backlog. Dividing actual load-path CPU by per-call cost implied ~2/s steady, only ~1.5 ms/s. The design could matter during joins but did not ship. Elsewhere, client-side-generation eligibility repeatedly queried existence/blending caches: later target profile 19.1 of 93 ms, ~700,000 queries/s steady and 1.6m walking. Both caches wiped entirely at their caps, thrashing the working set. Custom cache a46a12cdb saved ~11 ms in a prototype, then was replaced by raising original caps (2bf178a99), retaining established invalidation. Wipes then estimated once/25 minutes. No isolated cap-raise benchmark; do not assign custom-cache saving automatically to its simpler replacement.

### client-vs-server.md — Idle workers can beat a larger pool {#client-vs-server-md-idle-workers-can-beat-a-larger-pool}

An i7-14700F has 8 P cores, 12 E cores, 28 threads. Windows BDS counted only two-thread cores and used min(core-count, max-threads)−1; default max-threads=8 gave seven workers. Raising it to 16 on that machine still gave seven. Linux counts differently but default also capped it. The game had 23 workers, without a fully traced derivation. A test ceiling lift gave 15 workers, only four active; stock had only two or three active. Pool backlog threshold, not lack of threads, withheld wakeups for short tasks.

cd97eea16 sets the threshold zero, waking an idle worker for any queued task while preserving pool size. Small nonzero threshold A/B cut median view 132 to 86 s and p90 248 to 205, with join TPS 18.2. The shipped zero run averaged 19.9 / min 19.2 TPS but stopped after joins and has no standalone view-load result. Fifteen workers with four active gave 83 s; bottleneck beyond about four busy workers was suspected elsewhere, not proven. Steady TPS/memory did not change. Hands-on flight/portal observations are anecdotal, not the capacity A/B.

Endstone also stopped forcing client-side generation false on new servers. Flat/void/legacy worlds differ. Comparing 100 versus 450 sent chunks without this configuration is misleading; release numbers use enabled client-side generation.

### opt-genscheduler.md — Separate scheduling cost from pool utilization {#opt-genscheduler-md-separate-scheduling-cost-from-pool-utilization}

A 1.26.51 worker profile with shims spent 54% on selecting work. Score all waiting chunks against players/ticking areas, sort, launch a small batch. Sorting 0.55 ms inferred ~25,000 queued chunks; scoring 50 ms across 2.5m pairs implies ~20 ns/pair. Launching 29–42 tasks/pass caps throughput ~500–730/s; 1.6 busy cores included only ~0.7 actual generation. ### opt-network-thread.md — Measure saturation and all co-tenants before adding concurrency {#opt-network-thread-md-measure-saturation-and-all-co-tenants-before-adding-concurrency}

Post-login packet sends share one worker with telemetry, HTTP, DNS, discovery, signaling, login checks and script networking. At least one co-tenant assumes unlocked single-threaded bookkeeping. The article uses ~70% as a practical queueing ceiling, not a measured universal bound. Peak minute 238 ms/s and steady 46 were nowhere near saturation. Faster libdeflate, Endstone packet-path work and unused debugging removal together cut first minute 238→62, whole join 99→45, steady 46→40 ms/s. They were bundled; no isolated credit to one change. ### nethernet-cost.md — Models need a transport-specific validation plan {#nethernet-cost-md-models-need-a-transport-specific-validation-plan}

All published measurements here still use RakNet despite NetherNet warnings. NetherNet/WebRTC involves signaling, ICE/STUN and encrypted UDP data channels. Windows network wake loops rearm and poll all session sockets, Linux epoll only readiness. Two players produced four sockets (interfaces matter). About 1.1 μs rearm + 0.9 μs status per socket, measured with ctypes microbenchmarks subtracting a baseline, gives a model: 100 players × 20 input datagrams/s × 100 sockets × 2 μs ≈0.4 CPU seconds/s. At 50, 0.1; 200 extrapolates 1.6 and must saturate/batch before that. ACKs, timers and second interfaces add cost; these are modeled terms, not a 100-client NetherNet run.

Per-frame session lookup/locks must be compared with RakNet's stats copies and priced at loaded frame rate. Join certificate/key generation was expected to take milliseconds, not timed; login still exchanges keys before discovering transport encryption already exists. A shared socket reduces wake scans but incoming packets and ICE checks still visit sessions. Wrong-session unauthorized replies can cancel a client's pending check before the right answer. A development branch enabled shared socket and suppressed stray replies together; two real clients joined on one port, four sockets became two. No isolated validation and not shipped. The 0.11.11 one-port default without sharing prevented a second client binding; reverted in 0.11.12. Preserve that reversal rather than recommend the old default.

## Revision discipline and practical retrieval {#revision-discipline-and-practical-retrieval}

The twelve-post factual repair is meaningful source evolution, not cosmetic voice cleanup. In addition to the corrections above, it clarifies dedicated-server/client branches, inferred versus counted walks, unbuilt versus built ideas, grouped versus isolated A/B runs, and exact workload/version scope. The later restoration does not undo those corrections. Read the corrected state for current teaching, retain original claims only to explain the reversal.

For diagnosis: begin with bot state, actual server-confirmed commands, trace completeness, profile-cache isolation and dimensional units. For optimization choice: establish multiplicity, working-set size, cold-memory dependence and individual thread utilization, then compare safe smaller intervention against rewrite/parallelization. For behaviour preservation: specify RNG consumption, ordered iteration, lifetime checks, hash and arithmetic compatibility, notification completeness, fallback and explicit allowed variation. For benchmark review: retain failed runs, config adaptations, profiler overhead, concurrent load, actual simulated features, receipt-versus-load stage, and inferred versus directly observed evidence. For future research: warmup-alone A/B, real-client teleport tests, corrected clustered movement, entity-dense farms, shared-subchunk cache, generation throughput, and NetherNet-scale load remain open questions in these posts, not completed work.
