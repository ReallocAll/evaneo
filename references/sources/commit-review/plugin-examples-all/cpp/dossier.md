# C++ example plugin: a starter scaffold continually repaired against its host {#c-example-plugin-a-starter-scaffold-continually-repaired-against-its-host}

## Scope and reading {#scope-and-reading}

All 87 commits in the reviewed history range, from 2023-08-21 through 2026-07-25, are individually accounted for in [the ledger](ledger.md). Four merge commits have every parent delta examined, with imported authorship separated. Five other commits were read: four ancestors and one unmerged C++20 proposal. Public commit references and Git object comparisons support DAG/equality checks, not semantic correctness by themselves. No old Nukkit material is used. The teaching repository is a narrow genre: source conventions here must not become universal C++ policy.

## 1. Initialization is a connected set of identities and interfaces {#1-initialization-is-a-connected-set-of-identities-and-interfaces}

[C002](ledger.md#c002) starts with a shared library, exported plugin entry, lifecycle logs, explicit C++20 and CMake 3.25, with a small header/source pair. [C005](ledger.md#c005) changes packaging and SDK include targets; [C014](ledger.md#c014), [C027](ledger.md#c027), [C049–C052](ledger.md#c049) repeatedly coordinate CMake project identity, binary prefix, macro metadata, display prefix and documented artifact name. These are different fields with distinct consumers. A copy-and-rename operation must inspect all of them rather than replace a class name alone.

[C033](ledger.md#c033) moves commands/permissions and metadata into the ENDSTONE_PLUGIN builder, while onEnable retrieves the command and conditionally attaches an executor. This makes the public declaration versus lifecycle setup boundary visible. Later [C068](ledger.md#c068) uses direct onCommand for two simple commands. The macro is an Endstone loader convention, not a recommendation to use macros for every application initializer.

The current snapshot CMakeLists lines1–23 declares C++20, exposes ENDSTONE_API_VERSION, fetches SDK, configures a version header and invokes endstone_add_plugin. src/plugin.cpp lines1–36 supplies exported identity and independent public/operator permission defaults. A practical initialization checklist follows the dependency edges: project name → generated macro name → entry macro → SDK helper output convention → CI upload glob → documentation → release workflow. Missing any edge can leave a build that compiles under a wrong identity or packages the wrong artifact.

## 2. Dependency choices are contingent, with real reversals {#2-dependency-choices-are-contingent-with-real-reversals}

[C005–C008](ledger.md#c005) introduce Conan, add CI for it, then replace it with FetchContent on the same day. C008 explicitly says “better flexibility”; this is strong evidence of the choice in this starter's context, not evidence that Conan is always unwanted. Hand-maintained fmt and Endstone targets bring compiler, PIC and platform flags that [C009–C010](ledger.md#c009) immediately correct.

[C043](ledger.md#c043) delegates more to FetchContent_MakeAvailable and deletes setup boilerplate. [C045](ledger.md#c045) restores ABI/link flags under a compilation-fix message. [C049](ledger.md#c049) scopes options PRIVATE to the target; [C053](ledger.md#c053) then moves responsibility to endstone_add_plugin. The lesson is to inspect what the helper actually supplies at the selected SDK revision before deleting local policy, not to infer that fewer CMake lines always preserve behavior.

Tracking main, version-looking refs and pre-release main all occur: [C054–C059](ledger.md#c054) and [C063/C067](ledger.md#c063). [C076–C078](ledger.md#c076) expose the SDK version as an overrideable cache value and add the v prefix only when constructing GIT_TAG. Crucially, [issue8](../thread-context/analysis.md) explicitly calls v0.11 a branch. GIT_TAG is the CMake parameter name, not proof of an immutable tag. Branch-based fixes can arrive without a template commit, which helps fresh builds but limits reproducibility. Recording a resolved commit when diagnosing a build is an inference from that mechanism, not an attributed demand for immutable pins.

## 3. Toolchain/ABI diagnosis is more strongly supported than generic style {#3-toolchain-abi-diagnosis-is-more-strongly-supported-than-generic-style}

The history repeatedly distinguishes an installed compiler from the compiler CMake selects: [C009](ledger.md#c009), [C070](ledger.md#c070), [C082/C084/C085](ledger.md#c082), and [issue2's explicit diagnosis](https://github.com/EndstoneMC/cpp-example-plugin/issues/2#issuecomment-2321657859). Windows selects clang-cl after MSVC environment setup; Linux selects clang with libc++/libc++abi. README eventually uses per-command CC/CXX instead of system-wide alternatives, while ephemeral CI still uses alternatives. Therefore the narrow conclusion is explicit, environment-appropriate compiler selection, not a universal ban on alternatives.

[Issue1](https://github.com/EndstoneMC/cpp-example-plugin/issues/1#issuecomment-2255031670) connects a concrete iterator-debug-level linker mismatch to Debug ABI incompatibility with Endstone/BDS and recommends a clean Release/RelWithDebInfo build. [C046](ledger.md#c046) chooses RelWithDebInfo and retains PDBs; [C047](ledger.md#c047) excludes fmt.pdb using narrower artifact globs. This is diagnostic distribution practice under a native-host ABI constraint. No runtime or debugger session is demonstrated.

[C072/C079](ledger.md#c072) teach the GLIBC_2.xx-not-found symptom and recommend an older build OS. The broad README statement about Ubuntu 24.04 versus 22.04 is a source claim, not a universal binary theorem: actual dependencies/symbol versions matter. The useful portable response is to inspect required versus available symbols and choose a compatible baseline. This assignment did not inspect a built binary. [Issue8](https://github.com/EndstoneMC/cpp-example-plugin/issues/8#issuecomment-5078967789) attributes a later failure to the SDK branch; adding template flags was the reporter's unsuccessful experiment, not the maintainer's endorsed fix. The exact SDK correction remains outside this commit review.

## 4. Example complexity is intentionally reduced, then must still be correct {#4-example-complexity-is-intentionally-reduced-then-must-still-be-correct}

Early Fibonacci illustrates command registration, executor ownership, argument grammar and permissions. [C018](ledger.md#c018) changes from “first n terms, capped at20” to “values below n” and removes the cap. That is a behavioral change, with potential integer-overflow risk and no added preservation test. A commit titled refactor/improve cannot be assumed behavior-preserving. [C019–C021](ledger.md#c019) replace command subclasses with API parameters but first swap arguments and use the wrong command name; tiny corrective patches are meaningful.

[C031](ledger.md#c031) adds fine-grained permissions. [C061](ledger.md#c061) removes an operator-only child from a default-True parent and explicitly calls the hierarchy incorrect. This is useful access-control evidence: check effective permission propagation, not only the label on each node. It does not license treating every API's permission graph identically.

[C068](ledger.md#c068) explicitly says Fibonacci is too complex for a starter template and replaces it with hello/broadcast plus join/quit. The current example teaches sender type checks, argument handling, public versus operator command permissions and a separately owned listener. It does not establish that Fibonacci, separate executors or advanced event behavior are bad design in a real plugin.

## 5. Layout and lifetime conventions are examples, not absolutes {#5-layout-and-lifetime-conventions-are-examples-not-absolutes}

[C006](ledger.md#c006) separates declarations and definitions, but [C013](ledger.md#c013) moves implementations back into headers and leaves the export macro in the source file. This direct reversal blocks a permanent “always split files” or “always header-only” rule. [C036–C037](ledger.md#c036) explicitly show handlers on the plugin and on a separate listener as alternatives. At HEAD, unique_ptr owns ExampleListener and the listener holds a Plugin reference. This explains the intended owner relationship but does not establish unregister/teardown guarantees across reloads; those belong to SDK lifetime contracts and need tests in a real project.

[C073–C074](ledger.md#c073) demonstrate a specific API audit: replace SocketAddress.toString with getHostname/getPort, then bind the value-returning getAddress with auto instead of auto&. The changed code is correct by its stated return-value premise; this assignment did not compile it. The copied AGENTS.md example line145 still calls toString. A tutorial or agent guide can drift even when compiled source is repaired. When adapting a scaffold, check current definitions and examples together.

## 6. A version source is useful only if release paths share it {#6-a-version-source-is-useful-only-if-release-paths-share-it}

The March 2026 reset uses a literal plugin version and a manual release workflow. [C081](ledger.md#c081) explicitly makes CMake project VERSION the single source: configure_file emits version.h, the entry macro consumes CPP_EXAMPLE_VERSION, and release updates CMake as well as CHANGELOG. Its message credits Claude Opus4.6; [C078](ledger.md#c078) also has that coauthor trailer. These two explicit credits must survive preference synthesis; no other AI involvement is inferred from style.

The final workflow validates version syntax, checks an existing tag and a nonempty Unreleased section, previews a dry run, edits/version-tags/pushes, creates a GitHub release, then builds and attaches Windows/Linux outputs. This provides useful precondition checks, but it is not an atomic release transaction: build failures can happen after the tag/release exist. Dry-run also bypasses builds. A new plugin should make its intended validation and recovery sequence explicit; this is a bounded adaptation recommendation, not evidence the original pipeline recovered successfully.

Forking requires changing the hard-coded repository guard and the `project(cpp_example VERSION ...)` sed target, alongside macro/target names. [C082](ledger.md#c082) fixes compiler selection in build.yml; collaborator MisledWater79's incoming patch is integrated only at [C087](ledger.md#c087) for release.yml. Separate build/release paths drifted, so check both. Attribution belongs to the collaborator for that patch and wu-vincent for integration.

## 8. Tests, limits and useful checks when applying this evidence {#8-tests-limits-and-useful-checks-when-applying-this-evidence}

No dedicated tests appear in the 87 reviewed patches or the final tree. CI compiles and uploads; README describes manual loading and expected logs. None of those artifacts proves a successful server load, command behavior, permission safety or ABI compatibility. No upstream code was executed.

Reasonable application checks, explicitly recommended rather than attributed/tested: configure from a clean cache with selected compiler and host-compatible build mode; record the resolved SDK commit; inspect the built binary name/export/ABI; verify hello/broadcast for player/console/other senders and public/operator users; verify missing/empty arguments and unknown command return; verify listener lifetime and unload behavior; build/release both platforms from the same version; compare generated guide snippets to real API declarations. These checks address observed failure modes and scaffold edges, rather than making a claim of universally optimal initialization.
