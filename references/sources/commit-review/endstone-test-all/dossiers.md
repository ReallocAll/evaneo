# Endstone test plugin: complete commit history {#endstone-test-plugin-complete-assigned-commit-review}

The commit-by-commit section links changes to their public sources. Merges combine parent histories; their changes and inherited authorship are described separately. The PNG added in `ea1e8a5` is a map-render test input.

This is static source analysis. No upstream source, plugin, test suite, build, or server was executed. A Python syntax parse does not check imports, runtime compatibility, or behavior.

At the endpoint, the source contains **33 Python files, 71 `test_` function definitions, 214 assert statements, and 46 decorated event handlers**. These are syntax counts, not collected parameterized cases, executions, passes, line coverage, or compatibility results.

Commit authorship follows the public GitHub history. The initial commit imports an example template and license; merge commits integrate work from both parents and do not transfer authorship.

## How to use the knowledge {#how-to-use-the-knowledge}

- For an embedded Python/native API regression suite, begin with [harness](#harness), [commands](#commands), and [stateful isolation](#player).
- For a binding identity, metadata-copy, missing-value, or exception-boundary problem, use [inventory](#inventory), [registry](#registry), [scoreboard](#scoreboard), and [blocks](#blocks).
- For manual gameplay diagnostics and coverage visibility, use [events](#events). Event occurrence is a different claim from assertion success.
- For concurrency or callback lifetime issues, use [asyncio](#asyncio), [harness](#harness), and [map](#map).
- For a migration, follow the explicit old/new behavior chains rather than copying a historical assertion into a current-version suite. The commit-by-commit sources below preserve additions, removals, and reversals.

This couples test prerequisites to the point at which native server objects actually exist: the earliest suite expects no levels at load and one at enable. ### Prerequisites, observability, and costs {#prerequisites-observability-and-costs}

The final plugin declares API version `0.10` and `PluginLoadOrder.POSTWORLD`. It creates the event dashboard, registers listeners, runs server-ready tests, then assigns the operational command executor. Player tests execute on each player join. A test run returns pytest's code, but the lifecycle callers do not check that code, disable the plugin, or stop command setup when it is nonzero. The earliest runner explicitly logged an exit code; final pytest emits its own output through `-s`. A running plugin or filled event dashboard therefore does not establish that tests passed.

Repeated in-process pytest is session-scoped per invocation, while the server and player objects are real shared mutable state. This makes native binding identity and live interoperability observable. It also means world/player changes, repeated pytest module/plugin state, and event callbacks induced by tests can matter. No reentrant/concurrent run guard is present. No independent subprocess, disposable server fixture, world reset, or client simulator is added in this history. These are review observations, not runtime failures demonstrated here.

### Build, dependency, release, and configuration evidence {#build-dependency-release-and-configuration-evidence}

The final `.github/workflows/build.yml` is byte-identical to the root file. On push/PR to main, it installs Python 3.9/3.10/3.11/3.12, upgrades pip, and runs `pip install .`. Its comment says it runs tests, but there is **no pytest/server/import invocation**. Passing this workflow cannot establish plugin runtime correctness. `match` statements and PEP 604 annotations in the source require newer language/runtime support than a claim of full Python 3.9 runtime compatibility; the 3.9 installation matrix is not evidence those files were imported successfully.

The publish workflow likewise remains unchanged and checks `github.repository == 'EndstoneMC/python-plugin-template'`. At this repository identity the guarded job is skipped. It would build an sdist and use trusted-publishing action under a `pypi` environment if the guard matched; no publication execution evidence is present. Do not infer a working release channel from the filename.

The final hatchling configuration declares version `0.0.1`, Endstone entry point `endstone_test:EndstoneTest`, Babel, Pillow, and `pytest==8.3.2`. It declares neither an Endstone runtime dependency nor NumPy despite imports; the host environment may supply those, but this history does not validate that assumption. Babel arrives for locale parsing; Pillow arrives for early skin export, is removed when exports are removed, and is re-added after skin exports return. The pytest pin is observed, with no stated reason. `bedrock_server/` is ignored from `76c9b69`. README becomes and remains a two-line purpose statement, so detailed live-server running conditions must be reconstructed from code. API-version bumps `7057521`, `c8f16c6`, and `7a90f07` are not broad compatibility test results.

### Application and counterexample {#application-and-counterexample}

Use this pattern when the system-under-test only exists inside a host process and identity/bridge behavior matters. Inject the actual host-owned object and select tests after its lifecycle prerequisites hold. Do not transplant it as a production safe-to-run suite: inventory clears, permissions, bans, movement cancellation experiments, file writes, and default-true command access make a disposable test server essential. This is a portable testing lesson supported by the code's effects, not a claim the author recommended production use.

## Commands, translation wrappers, forms, and scheduler behavior {#commands}

### Registration, identity, and executor lifetime {#registration-identity-and-executor-lifetime}

The early command metadata grants `endstone_test.command.test` by default to everyone. `213630f` checks command existence and `command.plugin is plugin`. `ce1bb0d` moves handling into `TestCommandExecutor`. The first pytest test assigns the executor and leaves it installed; operational command behavior therefore depends on running that test. [a62e062](https://github.com/EndstoneMC/endstone-test/commit/a62e0623e9f9ed8b247e296209354bb7c5fb9e20) improves the roundtrip: assign a newly constructed executor without another local reference, verify its Python subtype, restore the plugin, then verify it is no longer that subtype. The lack of a local executor variable makes the binding's ownership of the assigned object more observable than a local variable plus `is` comparison, although it is not a forced-GC lifetime stress test.

[03daa44](https://github.com/EndstoneMC/endstone-test/commit/03daa44930a2eabba3591b520341fca01e813d33) explicitly installs the command executor after pytest. This separates test mutation/restoration from setup. The later map feature adds a `Plugin` constructor argument and calls the executor base initializer; wiring and tests change together. Final executor switching tests restore inline rather than in a fixture, so an early assertion failure can leave a temporary executor, although normal enable then installs the intended one.

`player.perform_command("test sender")` is asserted in join-time tests. Console `execute as "<player>" run scriptevent ...` is only called; it has no return/output assertion. The server dispatch smoke test evolves from `say` to `scriptevent` and eventually asserts returned success; event reception is only logged separately. These tests cover different boundaries and must not be conflated.

### Capturing translated and string outputs {#capturing-translated-and-string-outputs}

[3db623d](https://github.com/EndstoneMC/endstone-test/commit/3db623de43b26b346ed1963a4876dc9fada428a2) constructs `CommandSenderWrapper` with `on_message`, translates received output using `server.language.translate(..., locale="zh_CN")`, dispatches `listd`, and asserts a Chinese substring for players online. This verifies command execution → wrapper callback → translation service → captured text, not just boolean dispatch.

The package move expands coverage to plain string `status` output and a custom sender command. [884f80e](https://github.com/EndstoneMC/endstone-test/commit/884f80eb73577163308d237f5e54c17a3b3c02f4) removes the custom sender case, installs an executor explicitly, adds `on_error` assertions, renames `command` parameter to `command_line` so the actual command fixture is available, and fixes the missing diagnostic f-string. Final cases are `listd` with Chinese text and `status` with `Server status`. A `locale` parameter exists but translation is hard-coded to `zh_CN`; this is not a real parameterized locale test. Callback exception propagation is assumed by this test's use of `assert False` in `on_error`, not independently demonstrated. Built-in command output wording changes can break the substring oracle even if dispatch remains sound.

### UI probes and parsing migration {#ui-probes-and-parsing-migration}

Forms evolve from sending a MessageForm and then ActionForm unconditionally to argument-selected `message`, `action`, or `modal` variants in `11bc153`. Non-player senders get an error and False. Submit callbacks echo selection; close callbacks echo the type; modal callbacks decode JSON before echoing it. Modal controls include dropdown, label, integer-step slider, step slider, text input and toggle, with specified defaults. Translatable title/content are exercised; buttons use an external image URL. `ActionForm.Button` later migrates back to standalone `Button` in `2e71048`, and translated types move to `endstone.lang`.

These are client/manual probes. Nothing programmatically clicks buttons, closes forms, asserts JSON control correspondence, validates the image fetch, or checks form queueing. The unused unknown-form branch's diagnostic is corrected to `form_type` in `8e9f096`, but the surrounding match only accepts known types. Command usage descriptors simplify from typed literal/enum declarations to `/test form <message|action|modal>` and other literal subcommands in `f6fb36e`. The parser is hosted in Endstone; this repository supplies declarations and handlers but no standalone parser implementation.

The selector probe is replaced by player toast/kick tests. Title implementation precedes its declared usage until `bd698d6`. Additional routes inspect block arguments, broadcast a sender-named message, generate a 20-point particle circle, play a fixed sound, inspect/edit held items, and finally spawn an entity at the sender's location. A successful handler return is often unconditional; it does not prove a client saw a particle/sound/title, an inventory edit took effect, or spawning returned the intended actor. Kicks, broadcasts, forced high-level enchantments and entity spawns change the live test environment. Default-true permission is a relevant deployment constraint.

### Scheduler history and removed save test {#scheduler-history-and-removed-save-test}

`9ed0a61` migrates separate delayed/timer methods to `run_task` with `delay` or `period`, preserving a 20-tick welcome delay and 10/20-tick periodic tasks. Early welcome captures scalar name/UUID, then name only; a later version resolves the player at callback time and asserts it still exists. A disconnect during the delay is an unhandled counterexample. The pytest refactor removes these recurring debug/ping tasks and makes welcome immediate.

[ec26121](https://github.com/EndstoneMC/endstone-test/commit/ec261217dbce13ea7a53e5d6468e611ef510a687) adds a save scenario explicitly annotated as a case study for [Endstone issue 31](https://github.com/EndstoneMC/endstone/issues/31). Code sends `save hold`, schedules `save query` five ticks later, captures translated output fields, and reschedules until query reports readiness, then asserts success and sends `save resume`. Its comment explicitly says the delay avoids blocking while saving. That rationale is supported by the comment. However pytest's test function returns after scheduling; the eventual callback assertions are not awaited by that pytest test, there is no timeout, and failure lacks guaranteed `save resume`. `3db623d` removes this entire test. It is useful historical evidence of nonblocking polling and its test-oracle limitations, not surviving regression coverage or demonstrated persistence safety.

## Event probes, observable coverage, and diagnostic costs {#events}

### From logs to an occurrence dashboard {#from-logs-to-an-occurrence-dashboard}

The history adds handlers for login/join/quit, teleport, death/damage/respawn, actor lifecycle/knockback/explosion, interaction, blocks, weather, commands, script messages, packets, inventory interactions, chunk lifecycle, beds, skin changes, portal/dimension transitions, and map initialization. Many handlers only access and log properties. The final count of 46 decorated handlers measures registrations in source, not verified behavior of 46 event kinds.

The major [f437de4](https://github.com/EndstoneMC/endstone-test/commit/f437de4447518f53d87a4af64185c532ddf23316) split introduces `ActorEventListener`, `BlockEventListener`, `PlayerEventListener`, `ServerEventListener`, `WeatherEventListener`, and a shared base; `40afdf7` adds level events. The base walks bound methods, selects `_is_event_handler`, checks exactly one parameter, checks its annotation is an actual class and an `Event` subclass, then tracks `event_cls.NAME` or its class name. This validates listener shape at construction and makes future registered handlers automatically enter the progress denominator. It does not accept arbitrary string annotations in that check without additional resolution.

The plugin creates the boss bar before constructing listeners, counts occurrences by event class name, logs first occurrence, computes how many event names have nonzero count, and shows the last still-untriggered name encountered. The displayed “Next” is a navigation hint, not a prescribed dependency order. When all registered names have nonzero counts it says all events triggered. A handler can reach the tracker and later fail or mutate state incorrectly; a single occurrence says nothing about alternate payloads, cancellation, priorities, ordering, duplicates, disconnect timing, or absent players. The tracker also assumes the registered NAME and runtime class-name keys agree. That consistency is not asserted.

`f33ba6b` adds `always_log=False` and removes duplicate unconditional chunk logs. Later interactions, pistons, beds, leaves, portal/dimension changes and map initialization use repeated logging; Item actor spawn gets special repeated diagnostics in `ac7e55a`. First-occurrence logging reduces emitted output, but payload formatting happens before calling the tracker, and each event still scans all tracked names and updates boss-bar state. Thus no measured high-frequency performance improvement follows from less logging. Packet events make this distinction particularly relevant. No profiler/benchmark or concurrency guarantee is included.

### Mutations and reversals are part of coverage {#mutations-and-reversals-are-part-of-coverage}

- `99befe9` deliberately cancels the first login using one shared flag; `97c54f1` removes it.
- Early join/quit probes broadcast separate messages, then mutate event text in `b2d5835`. Later translation handling adapts from strings to Translatable; `ac7e55a` suppresses normal join/quit messages with None; `d23b342` restores them by commenting out those assignments. Death messages similarly change from color concatenation to translated logging.
- `7536d91` truncates explosion block lists to one block. `25cb1bb` removes the mutation. No rationale is supplied by the source.
- `04b0ffa`, despite its style title, adds movement cancellation. `3b5bcf3` removes that cancellation and adds cancellation for dropping apples. The listener split adds golden-apple pickup cancellation; `2e71048` corrects the condition from the item entity's type to `event.item.item_stack.type`.
- `46fef5e` substitutes an apple for cooked cod in cooking results. Piston cancellation remains commented, so do not count cancellation coverage there.
- Kick reason is bold-prefixed; server-list response fields are altered. Their external appearance still requires client inspection.

These are controlled test interactions only in an isolated world. They can be useful for manually observing that native event setters/cancellation hooks change behavior, but a callback executing does not verify the expected outcome. The source does not include automated world/client assertions for those outcomes.

### Packet and player-data diagnostics {#packet-and-player-data-diagnostics}

Packet probes begin as comments, migrate event/data field names while still inactive, activate with ID filters in `b0d7494`, disable decorators in `fde3496`, then return active through the listener split. `04b0ffa` removes packet filters from the inactive bodies and bounds previews to 31 incoming or 30 outgoing bytes, shortens text, and handles `event.player is None`. Final packet listeners use those bounded previews and address fields; default tracker logging usually emits only the first event per type. No packet mutation or protocol decoding/assertion is performed.

The player logs include name, UUID, XUID, address, runtime ID, device ID/OS, locale and location. Early skin export is added, removed, and later restored on login under a style-labelled commit. Final code writes skin and optional cape images under `plugin.data_folder / player.name` using skin/cape identifiers as filenames and logs identifiers. It does not sanitize those path components locally, impose retention, or make image I/O asynchronous. Runtime filename constraints may come from Endstone or Minecraft; they are outside this source review, so an exploit is not claimed. For portable use, treat this as identifiable diagnostic output and disk-write cost, and avoid copying it blindly into production.

## Server state, configuration, bans, and host assumptions {#server}

The server tests illustrate using an existing command or configuration file as an independent path to observe a Python binding. The useful pattern is not the literal values but **state established by one interface, read or reversed by the other**.

### Levels, dimensions, players, and versioning {#levels-dimensions-players-and-versioning}

Early lifecycle checks count `server.levels`, compare `server.minecraft_version` with an exported version (first with a `v` prefix), and retrieve each level/dimension by name using `is`. `0acac8e` migrates to singular `server.level`; `b2d5835` changes version string representation; `ace344f` removes the version test entirely. Later `5bf29d4` asserts named overworld/nether/end dimension types; `7044558` adds missing dimension and player-name lookups returning None. Original random-UUID missing lookup assertions were removed during the first pytest extraction and are not present in the final suite. Positive UUID identity is still checked on join.

The final dimension test combines enumeration/lookup identity with known named dimension types. It does not create/remove dimensions or check unloaded-world behavior. Static identity assertions test stable Python object exposure at that moment, not native ownership over server restarts. Protocol version is logged from `03daa44`, with no correctness assertion.

### Maximum players and server.properties {#maximum-players-and-server-properties}

[e92b5eb](https://github.com/EndstoneMC/endstone-test/commit/e92b5eb320480ff0b010a3704cc3f850f0f5ff4b) runs `setmaxplayers 5`, expects `server.max_players == 5`, then sets `server.max_players = 100` and expects 100. The getter is tested against command-produced state, while the setter is a same-interface roundtrip. No original capacity is saved or restored. This can alter admission behavior on a live server even if all assertions pass.

`23de337` compares `server.online_mode` to a setting read from `server.properties`; `4a94686` resolves the relative path. [aef5b0e](https://github.com/EndstoneMC/endstone-test/commit/aef5b0ec770a02ce2a57ebcaf50fe898a54f696d) expands it to `online-mode`, `server-port`, and `server-portv6`. It reads the file two levels above the plugin's data folder, splits each line once on `=`, skips malformed/no-equals lines, converts booleans/integers, and requires exactly three matches. This catches a silently skipped required key. It also makes custom layouts, absent defaults, or duplicate matching lines counterexamples; the code does not query a canonical configuration path API or assert that the runtime reloaded a changed file. Reading the file is an oracle for initial configured values, not live reconfiguration testing.

### Bidirectional ban interoperability {#bidirectional-ban-interoperability}

[2361546](https://github.com/EndstoneMC/endstone-test/commit/2361546b2cd3ff1e0b7a3816b128e5a294b1c8e1) uses a fixed synthetic name containing spaces. One test creates a ban via `server.ban_list.add_ban`, checks membership/name/reason, dispatches quoted `unban`, and checks absence. The other dispatches a quoted `ban` command with a colon-prefixed reason and trailing space, checks the API exposes the normalized reason, removes via API, and checks absence. The name quoting and reason trimming are meaningful parser/API boundaries rather than incidental sample prose.

These tests mutate the server ban list. Cleanup is inline, so an exception can leave the synthetic ban behind, and an existing ban under the same fixed name can be overwritten/removed. There is no disk save/reload, expiry, source, case-normalization or active-user disconnection assertion. Do not infer durable persistence correctness from in-process list consistency.

## Player API checks and state restoration {#player}

### Identity and representation boundaries {#identity-and-representation-boundaries}

The initial player-name lookup is asserted with `is`. The UUID equivalent is explicitly commented as crashing in `72d5270` and enabled in `b1cce60`. This supports a before/after test-coverage fact; the upstream crash mechanism and fix are not in this repository. The final join test also checks online-player membership. It exercises the live wrapper identity for the joining player rather than just field equality.

Player ping consumption changes from `timedelta` division to direct millisecond-like value logging in `96175fb`. Locale parsing gains Babel and later normalizes hyphens to underscores in `661a8a0`, a concrete compatibility adjustment. The parseability assertion is not a locale roundtrip or all-locales matrix. Skin/cape arrays must have four channels at axis 2, later accessed as `image`/`cape_image` instead of `skin_data`/`cape_data`. The tests do not assert dimensions, dtype, pixel values, ownership, or memory lifetime; optional capes are only checked when present.

### Mutators with differing cleanup strength {#mutators-with-differing-cleanup-strength}

- Experience begins with increment and range checks, then direct level assignment. In the extracted player suite (`a9a7749`) it captures level/progress, adds two levels, sets one above original, inverts progress and checks with `1e-5` tolerance, restores both, and asserts restoration. Inline restoration is a meaningful improvement over leaving experience changed, but fails to run if an earlier assertion fails. The final exact restored-progress equality and pre/post relation assume the operations preserve the relevant floating representation.
- Speed setter tests set fly/walk to 0.5/0.05 and reset to fixed defaults, then `58ac99e` replaces them with getter checks against 0.05/0.10. Final coverage therefore checks defaults, not setters. Flight permission mutation/assertion is commented out by `c71be05` and later removed. Neither should be described as surviving tested functionality.
- `85d14c9` captures health, asserts default max health 20 and current bounds, sets 11, checks it, restores original, and checks it. Modified maximum-health gameplay environments can fail without a binding defect.
- Game mode is switched to spectator, read back, and restored to the original. This also triggers live events and client state changes.
- Name tag checks originally require `name_tag == name`, write Test, write empty, and leave empty. `4d3feb3` adds a final reset to `player.name`. This is a successful-path fix, not preservation of an arbitrary preexisting custom name tag or failure-safe cleanup.

### Tag semantics {#tag-semantics}

`f5f3b99` establishes/removes a tag with commands and verifies API membership. `2747647` adds direct `add_scoreboard_tag` success, duplicate-add False, direct removal success, absent membership, and repeat-remove False. Those last assertions test idempotency/result semantics, not merely mutation. A fixed `test_tag` and no pre-state capture mean existing tags and failures can influence the live player. Tests do not exercise tag limits, invalid names or persistence.

### Applicable testing lesson {#applicable-testing-lesson}

Preserve original state and verify the restoration where a test must share a live object. Prefer a fixture/finalizer for cleanup required after failure; this history contains both inline restoration and the stronger yield-based permission fixture, so it does not justify a claim of uniformly rigorous cleanup. An isolated/disposable player inventory/world is necessary because inventory tests deliberately clear contents. Current default assumptions (health, speeds, scoreboard, name tag and terrain) are valid only for the intended controlled test setup.

## Permissions: defaults, explicit overrides, and cleanup {#permissions}

The first permission probe checks `/me` is allowed, attaches False, checks denial, and calls `update_commands`. It leaves the attachment attached. `7044558` replaces this with op/non-op tests, capturing and restoring `is_op` inline. `b8ced0e` adds a /me denial and /kick grant and removes one op-ban assertion; again attachments persist.

[2fa0568](https://github.com/EndstoneMC/endstone-test/commit/2fa0568c77293ac12328745e9a236ac6f2275bf8) creates a `permissible` fixture: save original operator state, set False, yield player, restore state afterward. The test matrix checks:

1. Non-op gets ordinary `/me` but not `/kick` or `endstone.command.ban`.
2. Op gets those permissions.
3. An explicit grant enables `/kick` without turning the player into an op.
4. An explicit deny blocks `/kick` even while the player remains an op.

The distinction between permission decision and op status is meaningful. It catches an implementation that implements grants by elevating op or incorrectly lets op bypass explicit denial. The namespace changes from earlier `minecraft.command.ban` to `endstone.command.ban`; this is a concrete API/registration adaptation, not cosmetic string editing.

[3b5bcf3](https://github.com/EndstoneMC/endstone-test/commit/3b5bcf3f684525e5b7588899ac169449a29efb43) stores each attachment handle, removes it, and asserts fallback to the inherited decision: non-op returns to denied after removing grant; op returns to allowed after removing deny. The fixture restores op status even when a test assertion fails after yield. Attachment removal is still in the test body and can be skipped on failure. The suite does not test conflicting multiple attachments, removal callbacks, expiry, asynchronous permission changes, or client command-list resynchronization in its final form.

Use the matrix to audit privilege precedence across bindings. Keep the mutation/cleanup caveat attached; this is not authorization to run it against production accounts or evidence every permission path is safe.

## Scoreboards and boss bars: identity, independent setup, cleanup, and ranges {#scoreboard}

### Scoreboards {#scoreboards}

The first scoreboard work (`7b4ff16`) is a visual ping sidebar: create/reuse objective, select display slot, update player score periodically. It is removed by pytest extraction, so its client presentation is not a final automated check.

The extracted suite checks objective creation fields (`criteria.name == "dummy"`, default display name, absent slot, later absent sort order, exact name, and owning scoreboard identity), membership in objectives, and score set-state/value. Commands create objectives and set score=3; Python reads the resulting state. A nonexistent score must have `is_score_set == False`. This paired positive/negative check distinguishes absent score from a score whose value happens to be zero. The player-specific version uses `get_score(player)` rather than a string identity. Player scoreboard assignment checks default server scoreboard identity, switches to a newly created scoreboard, checks distinct identity, then resets to the server scoreboard.

The server-ready suite's autouse fixture removes the fixed `test_objective` before and after each test and asserts absence. Later it avoids issuing removal if absent. That protects later tests after a failure in a test body, but also destroys any preexisting objective using that name. The player suite initially has the same yield fixture; `2747647` removes it and places deletion at the end of the score-value test. This weakens cleanup after failures and drops pre-test normalization. Server command quoting for player names is also absent in the scoreboard-value interpolation, unlike ban/tag tests, so names containing spaces are an unhandled fixture assumption.

A particularly important limitation: `test_remove_objective` calls `objective.unregister()` but does **not** assert absence immediately afterward. The final cleanup fixture conditionally removes the objective through a command if it remains. Therefore a no-op `unregister()` could pass this test as written; teardown masks the missing assertion. This is a concrete counterexample to interpreting a named test as complete API coverage. The final player scoreboard test resets to `server.scoreboard`, not an arbitrary original custom board, and assumes default identity at entry.

### Boss bars {#boss-bars}

The manual boss command in `a73afa3` creates a red segmented bar, sets 0.75 progress, and adds the invoker. `f437de4` replaces that route with the shared event dashboard, adds joining players to it, and removes all players on plugin disable. This demonstrates use of membership but does not assert membership behavior.

[e3cc915](https://github.com/EndstoneMC/endstone-test/commit/e3cc9150c64366a1126444650ef72b0d42459fec) adds three pytest functions: creation must preserve title, exact enum identity for green/solid, and default progress 1.0; sampled valid progress values include both endpoints and quarters; values below/above [0,1] raise ValueError. Boundary checks are meaningful for validating native range enforcement and Python exception translation. They do not cover NaN/infinity, invalid enum/title types, updates reaching the client, player membership, lifetime/persistence, or every float. Individual temporary bars have no explicit removal/destruction check. The comment about many APIs defaulting to full progress is an explanatory comment, not measured cross-API evidence.

## Blocks, block data, overloads, and environment-dependent oracles {#blocks}

`43df9b8` and `715c2f9` distinguish explicit and default block-state construction: standing-sign type, presence of `ground_sign_direction`, custom 8 versus default 0, and absence of unrelated `block_light_level`. These check that supplied native state maps round-trip and defaults are populated. The absence assertion is meaningful because it can expose accidental inclusion of unrelated property sets. `b91f618` adds the exact runtime ID `2761757297` for the custom state. That golden value is useful for the version under test but can change with game data; no cross-version stability is proven.

`dfc9be7` exercises `Dimension.get_block_at` overloads with integer coordinates and a Location. It assumes bedrock at y=-64 and air at y=320 at the player's x/z, then checks `block.data.type == block.type` for a location lookup. This is not valid for every dimension, custom world, void map, altered bedrock column, or unloaded chunk. It also does not compare overload results at the same coordinates beyond the type consistency check.

The negative boundary test changes materially: `ec26121` expects RuntimeError and the text “outside of the world boundaries” for y=-256; [5bf29d4](https://github.com/EndstoneMC/endstone-test/commit/5bf29d476bf4bc44a287a3a0f3f0ca496f23dc9c) instead expects an air block. This is an explicit contract migration and a counterexample to treating old exception tests as universal guidance. No why is supplied by the diff.

`79e9579` adds three highest-block tests: returned Y is nonzero; x/z overload and Location overload return a non-air block. Those are smoke oracles. A lower solid block could satisfy them even if not highest, and a legitimate highest block at y=0 could fail. A stronger algorithmic test would control a column and assert the exact maximum, but no such test is in this corpus. This distinction is retained rather than proposing that all added tests are equally strong.

The `/test block` route only echoes arguments parsed through the block/block_states command declaration. Break/place/cook/piston/leaves handlers are covered under event probes; they do not mutate/assert world block state in a pytest fixture. No voxel-world persistence, concurrent chunk access, or unloaded-region memory-safety conclusion is supported here.

## Inventory, ItemStack, metadata, and native round-trips {#inventory}

### Distinguishing wrapper state from server inventory state {#distinguishing-wrapper-state-from-server-inventory-state}

`e9d40c2` starts with slot-35 set/get; `918b82f` separates inventory tests and checks type plus amount, None clearing, and invalid identifiers. [15a5d56](https://github.com/EndstoneMC/endstone-test/commit/15a5d56db584e2d61b4ea59bd8ee465de7a2ef2c) expands the suite substantially:

- Clear the live inventory and assert `is_empty`.
- Use a `give` command to create a clock, assert nonempty, and compare `get_item(0)` with `contents[0]` for type/amount.
- Add seven clocks and check the returned slot; later add two cobblestone and check slot 1.
- Set seven diamonds in slot 35, retrieve, set the retrieved item again, retrieve again, and check `first(item) == 35`.
- Obtain item metadata, modify lore, call `set_item_meta`, reread metadata, write the modified item back to the inventory, retrieve it, and assert lore survives.

The explicit metadata commit and inventory re-read matter. A mutation that only affects a detached Python copy could pass a setter/read on the same local object but fail when the server inventory reconstructs the item. This suite has examples that cross that boundary rather than assuming it. However the “remove lore” tail only checks the local item after changing metadata, without another inventory write/read. Keep the exact scope of each assertion.

The suite is destructive: `clear()` loses preexisting items; other cases overwrite slots 0, 1, 2, and 35 without preserving contents. Add-item expectations depend on earlier tests clearing inventory and on no concurrent gameplay or plugins filling slots. Tests have no shared reset fixture and may fail when run individually or in a different order. New ender-chest size assertions in `6ba7602` and `ac45466` are the exact same patch on different branches, verified by identical before/after blobs; they are not independent repeated evidence. Final size checks expect 36 ordinary slots, 27 ender-chest slots, and max stack size 254 for both. Do not conflate an inventory's advertised stacking limit with the constructor's numeric validation range below.

### Invalid inputs migrate to constructor validation {#invalid-inputs-migrate-to-constructor-validation}

Originally an unknown item is constructed, assigned to a slot, and expected to read back None. [371c107](https://github.com/EndstoneMC/endstone-test/commit/371c107ff5013d06653755f9e0bfd5e5350a14b8) removes that test and expects ItemStack construction itself to raise RuntimeError for an unknown type. It also checks amounts -1, 0, and 256 raise a specific message documenting a 1–255 range. The tests validate rejection of those samples; they do not explicitly construct every valid endpoint, test noninteger/NaN inputs, or show native-side storage widths. `ff74787` updates the invalid-type error expectation to include canonical `minecraft:` and adds bare `apple` alongside namespaced `minecraft:apple`, making normalization behavior observable.

Known ItemType attributes begin with diamond sword durability 1561/max stack 1 and apple 0/64. `55ab343` adds Chinese translation-key results. `ca454a4` adapts to an API where `ItemStack.type`, `ItemStack.max_stack_size`, and `ItemStack.translation_key` are tested directly and adds potion data 0/7 with distinct Chinese names. The stack test's `max_durability` parameter remains in the table/signature after its assertion is removed, so its presence is not coverage. The typed registry still separately asserts sword durability. Later migration is not simply string formatting.

### Metadata semantics and coverage strength {#metadata-semantics-and-coverage-strength}

`91499fe` adds standalone checks for setting lore, clearing via empty list, and clearing all metadata via `set_item_meta(None)`. The observed assertions focus on `has_lore` and lore content; clearing every possible field is not tested. `21618b7`, despite a style title, changes empty-lore expectation from `is None` to falsiness in standalone and inventory tests. That intentionally permits multiple empty representations; it weakens an exact representation contract while retaining emptiness semantics. The same commit parameterizes metadata class expectations: air has None, apple/sword have ItemMeta, filled map has MapMeta.

Inventory round-trips then cover display name “Excalibur”, multiline lore, damage 500, and sharpness 66, with protection absent. [c77e489](https://github.com/EndstoneMC/endstone-test/commit/c77e489f40d058b7d4afd206d1eeeeec634979ef) explicitly checks an out-of-normal-range enchantment level is rejected when `force=False` and accepted when `force=True`, then confirms the resulting data after inventory storage. This distinguishes validation policy from serialization. The UI metadata command later uses force=True with level 10 but does not assert its success.

[175725b](https://github.com/EndstoneMC/endstone-test/commit/175725bd58b9b66b9b8cc2c8126eb68bc582b3ab) adds a fixture with `direct` and `inventory` variants. Both create a diamond sword; the inventory variant sets slot 0 and retrieves it. Parameterized tests then modify/read colored display names, two lore lists, sharpness/knockback add/remove, and damage 0/5/100. These test returned-item behavior on both construction paths. They **do not** re-fetch the inventory slot after each metadata edit, so they alone cannot prove the edit was persisted back to the inventory. The earlier explicit set/get roundtrip is complementary evidence. Type-hint-only `2c6838d` and the sample lore typo `c4d92ee` are verified concise mechanical dispositions, not separate engineering principles.

Use these cases when auditing copy-versus-reference bindings, metadata commit APIs, nullable values, exception translation, or tagged item variants. Avoid claiming durability across saves/restarts, data-version upgrades, network replication, arbitrary NBT fidelity, or all metadata subclasses: those are absent from the observed tests.

## Registry contracts: key types, nullable versus throwing lookup, and API migration {#registry}

The registry sequence is a compact but substantive API-surface audit. `f730d7e` checks enchantments using bare strings, namespaced strings, NamespacedKey objects, and a missing value. `371c107` adds item-registry membership. [825c2b6](https://github.com/EndstoneMC/endstone-test/commit/825c2b61b3c35f5a8166690980589ff75a608266) expands positive and negative matrices across protection/sharpness and diamond/diamond sword:

For a present key, the tests require non-None results from get, indexing and get_or_throw, together with successful membership. For a missing key, get must return None and membership must be false, while indexing and get_or_throw must raise KeyError. This is an analytical summary of the matrix, not a quoted source-code block.

The initial matrix tests NamespacedKey and string paths, compares `get_or_throw(ns_key) is get(ns_key)`, and checks known attributes (enchantment start/max levels, item stack/durability limits). `1d2ae72` adds the missing negative string-indexing case rather than assuming the object-key branch covers it. These are meaningful distinctions between Python mapping behavior, optional lookup, strict lookup, and wrapper identity.

[ca454a4](https://github.com/EndstoneMC/endstone-test/commit/ca454a496a784287d6be24dcd3932df895a84114) removes NamespacedKey usage and the identity comparison, preserving string-key success/failure/value checks. [5278e4c](https://github.com/EndstoneMC/endstone-test/commit/5278e4cd7b1eee0975a179187c61f51db9829b4b) changes registry selection from dynamic `getattr(server, "<kind>_registry")` to `server.get_registry(Enchantment)` or `server.get_registry(ItemType)`. The TypeVar annotation describes the input class, while runtime tests still validate concrete results. `ff74787` adds enchantment constants as keys and validates their `id` fields. No `isinstance(result, registry_type)` assertion is added, so “typed registry tests” should not be inflated into comprehensive returned-type validation.

The final suite does not cover iteration, registry size, mutation, plugin registration/unregistration, lifetime across reloads, unknown registry classes, or invalid key types. Fixed game-data attributes can change legitimately with versions. The history supports an API migration and an explicit negative lookup contract, not a preference for any one registry architecture or a proof of all native collection semantics.

<a id="asyncio"></a>

## Async scheduling: added, removed, reintroduced, and bounded claims {#asyncio}

### First suite and its removal {#first-suite-and-its-removal}

[263d564](https://github.com/EndstoneMC/endstone-test/commit/263d5640e81fc09d658580cdddf64bf902b7c524) tests `endstone.asyncio.run(coroutine)` in two ways. First, submitting a coroutine that sleeps 0.5 seconds must take less than 0.05 seconds; the returned object must expose `result`; its returned thread ID must differ from the caller; recorded start/end timestamps must bracket at least the requested sleep. Second, independently submitted 0.5/0.7-second sleeps return their expected values and finish between 0.7 and 1.2 seconds, intended to establish overlap.

The source explicitly states these intended meanings in docstrings/comments. The thresholds are test expectations, not benchmark measurements collected in this review. `time.time` is wall-clock, and sub-50ms submit plus upper-duration thresholds are susceptible to load/clock changes. Calling `.result(timeout=...)` blocks the test caller even though scheduling is intended to be nonblocking. `hasattr(result)` is a Future-like check, not strict `concurrent.futures.Future` type validation despite the comment. This entire file is deleted in [7044558](https://github.com/EndstoneMC/endstone-test/commit/7044558520c8bb18429831433c73ce494e15c9e0), four days later, without an explicit reason. Do not silently preserve it as continuous coverage.

### Second suite and what it actually proves {#second-suite-and-what-it-actually-proves}

[88f2178](https://github.com/EndstoneMC/endstone-test/commit/88f2178be7ffdea739d56f08128f82c9e5bf237c) reintroduces tests for `submit`, later moved to `on_enable`. It uses `perf_counter` for a gathered batch of three 0.1-second sleeps and expects returned `[0,1,2]` within 0.09–0.3 seconds. A single submitted coroutine runs `gather`, so this case validates overlap inside that coroutine; the separate 100-task case exercises repeated independent submissions.

Additional cases reject an integer and a generator with TypeError, propagate an asynchronously raised `ValueError("boom")` through `.result`, and submit 100 short tasks whose results must equal squares 0²…99². Each future has a timeout. The 100-task result list establishes successful completion under the run conditions, not a general fairness/starvation theorem or a single strict global deadline. The suite no longer explicitly measures call-return latency or compares worker thread identity. “Do not block” in a test name does not restore those removed assertions.

The test runner executes in plugin enable and synchronously waits for these futures. There is no cancellation, loop shutdown/restart, after-disable submission, backpressure, unawaited coroutine cleanup, deadlock/reentrancy, exception-group, or cross-thread native server-access test. The event-loop implementation is outside this repository, so its threading architecture cannot be inferred from the API name. The reusable lesson is to make independent claims observable (submit latency, completion, overlap, failure propagation, invalid input, lifecycle) and keep timing/environment caveats, not to treat a short timing assertion as a measured performance guarantee.

## Cross-history synthesis and restraint {#cross-history-synthesis-and-restraint}

This history supports several concrete reusable practices: test real host objects at the lifecycle where they exist; compare APIs against independent commands/configuration; check identity where wrapper preservation matters; distinguish detached-object updates from inventory reconstruction; test optional versus throwing lookups; make negative boundaries explicit; and separate event occurrence from semantic correctness. It also supplies counterexamples: cleanup can mask a missing removal assertion, test setup can accidentally become application setup, a directory rename can temporarily break selection, and a “style” title can hide behavior changes.

These observations describe specific code and test examples, not universal architecture rules. No measured execution outcomes accompany them; CI configuration was inspected but not run, and no runtime safety certification is implied. Small formatting and version changes remain visible in the commit-by-commit sources.
