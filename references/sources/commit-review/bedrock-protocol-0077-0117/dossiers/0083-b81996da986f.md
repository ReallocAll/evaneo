# 83. feat(compiler): generate a packet registry keyed by wire id {#83-feat-compiler-generate-a-packet-registry-keyed-by-wire-id}

Source: [b81996da986fdf61dfd2188331aa27a1380ae928](https://github.com/EndstoneMC/bedrock-protocol/commit/b81996da986fdf61dfd2188331aa27a1380ae928)

## Problem and constraints {#problem-and-constraints}

Per-module code generation cannot build one closed registry that sees every packet, yet consumers need wire-id dispatch.

## Implementation and producer semantics {#implementation-and-producer-semantics}

Add packet_of<V,Id> defaulting to void, packet_of_t and has_packet_v. Every generated module specializes its own packet ids; versioned entries return existing Name_<V> selectors and constrain the whole [earliest fresh snapshot,until) range. protocol.hpp inclusion supplies all specializations.

## Stated rationale and alternatives {#stated-rationale-and-alternatives}

One specialization per logical packet avoids snapshot duplication. Full availability bounds prevent future packets from appearing before introduction. Disjoint id ranges are intended to coexist. Compile-time id walking via MinecraftPacketIds END_ID is claimed to prune unmodeled branches.

## Tests and outcomes {#tests-and-outcomes}

Static known-id/type equality, void unknown/out-of-range ids, introduction boundaries for348/345, model counts17/18/18 and id agreement.

These are tests and outcome claims examined in source. No upstream test, compiler, codec, regeneration, Windows or BDS execution was performed by this review. The cited source/byte checks are static observations, not independent runtime validation.

## Limits and counterexamples {#limits-and-counterexamples}

Module-only includes intentionally see an incomplete registry. Message's byte-identical regeneration and dispatch equivalence are reported, not independently rerun. Initial _packet_entries uses one selected declaration's packet id/until; later changes must be consulted for richer histories.
