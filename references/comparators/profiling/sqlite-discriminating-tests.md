# Test whether the answer could have been wrong {#case}
## Context and actual choice {#section-01}

SQLite's official testing account distinguishes executing a branch from demonstrating that it affects an observable result. Its mutation approach alters generated branches and asks the suite to detect the change. It explicitly recognizes performance-only mutations whose results remain correct, and states that maintaining full MC/DC is costly and may not be economical for typical applications. It also reruns tests using delivery compiler options after coverage instrumentation. These are project-reported practices, not tests rerun for this supplement. [S01: coverage, mutation, and cost](https://sqlite.org/testing.html#coverage)

The separate TH3 description says its mutation driver changes branch instructions into unconditional transfers or no-ops and looks for test failures. TH3 is not a freely available test suite that this report inspected or recommends importing. [S02: TH3](https://sqlite.org/th3.html#mutation_testing)

There is also inspectable public implementation evidence. SQLite 3.46.1's fault-test harness has transient and persistent OOM/I/O configurations. For each failure position it prepares the case, injects the fault, runs the body, disables injection, and executes the test oracle. By default the loop stops when no fault was injected; callers can also cap it with `-end`. Its allocator wrapper tracks failures through a countdown and repeat count. [S03: public fault harness](https://github.com/sqlite/sqlite/blob/f3d536d37825302e31ed0eddd811c689f38f85a3/test/malloc_common.tcl#L26-L50), [iteration and oracle](https://github.com/sqlite/sqlite/blob/f3d536d37825302e31ed0eddd811c689f38f85a3/test/malloc_common.tcl#L326-L391), [S04: allocator injection](https://github.com/sqlite/sqlite/blob/f3d536d37825302e31ed0eddd811c689f38f85a3/src/test_malloc.c#L29-L128)

**Version boundary:** source inspection is pinned to SQLite 3.46.1. The two official explanatory pages were retrieved on 2026-10-20; they are unversioned documentation snapshots and must not be presented as exact 3.46.1 documentation. No TH3 implementation, full coverage result, or database test run was available here.

## Alternatives and rationale {#section-02}

This is our analysis of how much to borrow:

- A **smoke test** answers whether one scenario completes. Useful for installation, insufficient for a subtle ownership or measurement contract.
- **Coverage** identifies unexercised code and conditions; it does not show that the assertion would notice a wrong output.
- **Golden files** can detect unwanted changes but may preserve an original bug, especially when generated by the same serializer being tested.
- **A few selected mutants and fault positions** directly challenge the risk under review. They are often a cheaper first step than deploying a broad mutation platform.
- **Independent decoding/reference models** reduce the chance that producer and checker share the same error. They still need a precise semantic oracle and accepted version.

SQLite provides an existence proof for serious investment in oracles and adverse conditions. Its scale is a counterexample to “copy every mature practice”: a profiler plugin should justify each extra harness, dependency, and CI minute against its actual failure risks.

## A small Spark test plan with explicit wrong implementations {#section-03}

The rows below are original specifications motivated by the existing [Spark: profiler lifecycle](../../sources/commit-review/plugin-api-evolution/cases/spark-profiler-lifecycle.md) and [Spark: measurement and export](../../sources/commit-review/plugin-api-evolution/cases/spark-measurement-and-export.md) reviews. They are not newly verified defects or tests executed in this task.

| Contract | Deterministic stimulus and oracle | Plausible wrong implementation rejected |
| --- | --- | --- |
| Independent runs | Run A contributes frame A and window 0; run B contributes frame B and window 0. B's exported tree and counts contain B only. | Reset the timer but retain aggregation state. |
| Genuine median | Feed a deliberately skewed known duration set, such as 1, 2, 100. Verify a median-labelled field is 2; if the product only supports a mean, require an honest mean field/label instead. | Copy mean into median because smooth fixtures made them equal. |
| Capture lifetime | Gate a handler after it takes a buffer reference; stop; release the handler. Verify reclamation follows acknowledged completion. | Clear the publication pointer and immediately reclaim. |
| Tick completeness | Deliver a long tick's closure before its previously captured sample. Verify the documented acceptance/filter policy and accounting. | Treat drained closure as proof no sample can arrive. |
| Final loss report | Fill the queue, cause rejection, then stop without another successful enqueue. Final status includes loss. | Queue a loss notice only when capacity returns. |
| Local export intent | Start with local-save intent, then stop through the ordinary path. Fake transport observes zero network uploads; the expected local output is available. | Recompute destination solely from stop-time defaults. |
| Wire semantics | Decode a hand-built asymmetric fixture with a pinned independent protobuf decoder. Assert module/RVA identity, child references, sample-window alignment, and intended units. | Writer and its own checker agree on the same malformed encoding, or decode succeeds while meanings are wrong. |
| Recovery after error | Fail one acquisition/write operation, then all operations after that point. Verify an allowed terminal result, cleanup, and the next supported retry/run. | Handle the first error but leak or fail during cleanup/recovery. |

Do not use exact scheduling percentages as a deterministic unit-test oracle for a real sampler. Randomness, OS scheduling, compiler optimization, and unwind support change observations. Use fabricated sample streams to test aggregation exactly, and real workloads with statistically justified tolerances to test the actual capture path.

## Benefits, costs, and failure boundaries {#section-04}

Each test earns its place by naming a meaningful wrong behavior. This catches accidental weak oracles: a profile file existing does not establish that the right run, units, frames, or export destination were used.

Fault injection needs a narrow seam around a genuine external dependency, not an alternate implementation that replaces the component under test. A fake clock must not erase races the real clock enables; a fake exporter must preserve the ownership and completion contract. Keep integration tests for platform behavior.

Mutation results need triage. A surviving mutant can reveal a missing assertion, an irrelevant transformation, or a performance-only distinction; it is not automatically a production defect. Conversely, a timeout may kill a mutant without proving that the test diagnoses the intended semantic error. Record the expected failing assertion or safety tool, not only a red job.

## Verification implications and economical order {#section-05}

1. Start with run reset, skewed statistics, export intent, and hand-authored serialization fixtures. These have clear, inexpensive oracles.
2. Add gated lifecycle/interleaving tests for the specific ownership design. Use sanitizers or platform diagnostics where applicable, while keeping release-configuration tests separate.
3. Inject transient and persistent failures at resource and I/O boundaries, checking terminal state and recovery as well as error text.
4. For each repaired high-risk behavior, deliberately make one local test-only change that recreates the intended wrong behavior and verify the test fails for the expected reason; restore it before normal verification. This is a proposal for future authorized development, not an action performed on Spark here.
5. Run independent decode and real-platform integration checks, then measure overhead with the intended optimized build. Neither instrumented coverage nor deterministic models substitute for that result.

The desired improvement is a smaller number of tests with stronger discrimination, followed by expansion where failures justify it. Test counts and borrowed project reputations are weak acceptance criteria.
